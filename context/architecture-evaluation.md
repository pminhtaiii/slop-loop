## Controlled test-only ports

Controlled test-only ports in `tests/runtime/support/uc03/` simulate state, approval, model, repository and reviewer behavior with explicit finite profiles and mock provenance. They do not implement the real adapters or execution boundaries described in [architecture.md](architecture.md).

The restored [v0.2 entry](../src/uc03/graph-v02.ts) takes explicit production ports, checks required callable surfaces and provenance before dispatch, then uses the shared graph runner. [Host bootstrap](../src/runtime/uc03-host-bootstrap.ts) validates delivery pins and assembles without invoking ports; [workflow driver](../eval/uc03/workflow-driver.ts) selects this entry explicitly while retaining separate legacy controlled dispatch. The separate mock-only host assembly returns a tagged controlled-ready result and its versioned controlled runner cannot admit real-declared effectful ports; a controlled driver binding refuses a real evaluation context. Generation validates the canonical model context before v0.2 dispatch without a graph-side claim. Inspect results feed bounded observations into a freshly admitted next turn under the existing agent call/time limits; request identity reuse refuses. Feedback forwards the material-replan port. The direct evaluation shell parses operator references and resolves the host file's `assembly` module reference as a factory; a caller-supplied assembly wins outright, and every unresolved assembly — absent reference, absent file, absent or throwing factory, top-level throwing getter, non-object result — collapses to one named prerequisite gap with no path and no exception text, though a getter on `producers` or one of its members is dereferenced by `hostDeliveries` after `prepareAssembly`'s shallow copy and reaches the direct-execution tail as a generic exit 1 instead. An absent assembly is a gap, never a mock fallback. Assembly-ready is not behavior conformance or real execution authority; full traversal, approval-context consumption and real owner/profile gates require their own evidence.

## Feature 007 Phase 4–5 surfaces

Feature 007 Phase 4–5 adds three controlled-tier surfaces on that same graph/service. `src/runtime/evaluation-diagnostics.ts` defines bounded stage/component/attribution vocabularies plus a frozen sanitized record; `src/uc03/graph-diagnostics.ts` supplies the stage mapping and record construction, and `src/uc03/graph.ts` attaches one to a non-complete or unconfirmed-transition result, degrading unrecognised stage or component to `unknown` rather than guessing a cause. `eval/uc03/compare.ts` gains a tagged `compareWorkflowEvaluations` that refuses a pair on any failed identity guard (suite, contract version, mode, selection, manifest, cardinality, repository, grader, pinned initial repository, pinned expected outcome) and reports changed factors, null (never zero) usage deltas and mirrored selection/suite acceptance. Per-case repository, grader and pinned initial-repository identity are three separate guards; an identity the reports never observed (`null`) is reported as an unverified guard and refuses the pair rather than comparing equal, so two not-run reports cannot claim compatibility. `src/runtime/console-server.ts` serves the same `EvaluationService` over `node:http` bound to `127.0.0.1` with exact Host/Origin, an operator token, a 64 KiB body cap and serialised mutations, taking UC-05 approval/decision as an injected port rather than reimplementing it, and comparing either through an injected comparison port or, when none is injected, over a supplied workflow-report lookup; `src/runtime/console-page.ts` renders the operator document with `textContent`-only dynamic writes over static assets in `src/runtime/console-page-assets.ts`. The console now has a trusted same-process host: `createEvaluationConsoleHost` in `src/runtime/evaluation-console-host.ts` composes one readiness, graph, `EvaluationService` and console server, and `evaluate serve --host <path>` (`src/cli/evaluate.ts`, `src/cli/evaluate-console.ts`) starts it. Production serve requires real-ready provenance from `prepareUC03Host` and refuses controlled-ready or mock assemblies with `HOST_CONSOLE_UNAVAILABLE`; malformed arguments are rejected before the host module loads, validation precedes listening, shutdown is bounded, and a real-ready serve holds no workflow reports. The page projects only bounded allowlisted workflow-report fields via `textContent` (invalid or missing values show `unknown`, an ungraded report is custom), the result pane shows only allowlisted receipt/decision fields rather than raw JSON, a sanitizer strips C0/C1, bidi and line-separator characters, and artifact IDs are validated before fetch. One controlled loopback HTTP journey drives a single composed host/service/graph with the approval port a test double over scripted owner approval; its second attempt re-runs the delivered task, so the comparison is compatible/REGRESSED rather than two independent repairs. The open halves remain: no browser has driven the page (the page checks use a `node:vm` fake DOM), a successful full CLI serve was witnessed only through declared-real shell plumbing and not a real-ready acceptance, console comparison succeeds only in controlled composition (the host supplies a live-service report lookup and `console-server.ts` maps the page's `guarded`/`strict` selection onto `strictSameConfig` over it, while an injected comparison port still takes precedence; the graph binds workflow reports only on controlled-ready routes, so a real-ready serve comparison can only refuse with `WORKFLOW_REPORT_NOT_FOUND`), and sessions are process-local. The report carries one bounded `diagnostic` string, now composed from the graph's structured record's bounded component/attribution/reason codes; the record's evidence refs and milestone kinds are still dropped at that boundary.
