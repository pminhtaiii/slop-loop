# Incremental Evaluation and Shared Registration Contract

**Status**: DRAFT `uc01-evaluation-draft-v1`. The leader's evaluation-first direction is reported in the current user instruction (2026-10-17, Asia/Bangkok); detailed schema, registration and grading agreements with Tai remain pending. This document specifies proposed records and obligations, not an implemented runner, CLI, dataset or successful evaluation.

## Execution levels and authority

| Level | What can be established | Prerequisite / owner | What it cannot establish |
|---|---|---|---|
| contract | Data/result validation and deterministic grading-rule vectors | Approved UC-01 consumer contract; Thai, T002 | Model judgment, real adapters or runner compatibility |
| mock-behavior | Observable issue-to-outcome behavior with controlled injected ports | T003/T004 fixtures; Thai, T005–T010; early safety included | Real provider quality, durable recovery or product integration |
| real-integration | Actual guarded adapters, receiver validation, accounting/approval/restart evidence | T011–T013 and their external delivery/authorization gates | Held-out model accuracy or whole-project completeness |
| model-quality | Real-provider judgments on a frozen corpus with grader-only labels | A-PRODUCTION, A-EVALUATION; real integrations and Tai's runner available at T015 | Verification of unrelated UCs |
| project | Registered results for every required UC and required attack case | Tai's approved project manifest, runner and all required deliveries | Permission to infer missing/unrun cases passed |

Each slice follows: define behavior/criteria -> freeze relevant cases, inputs and grading rules -> implement only when authorized -> run every applicable available check -> retain result/failure evidence -> run impacted regression cases -> accept only with complete applicable evidence. Missing capability produces explicit not-run records and a blocker; it never grants a waiver. A task may finish its defined mock-level scope while separately required real-level cases remain not-run; it must not claim the latter scope complete. T016's final runtime gate requires all designated runtime-acceptance obligations, not merely mock-task completion.

## Case identity and versioned data

Proposed `PublicCase` fields are required unless marked optional. Text, collections and diagnostics are finite and sanitized under shared policy. These records are separate from the product [Invocation/Outcome](schema.md).

| Field | Meaning / validation |
|---|---|
| contractVersion | Literal `uc01-evaluation-draft-v1`; reject unsupported versions |
| caseId | Stable `UC-01:Cnn:variant` identity, C01–C22 with a nonempty immutable variant slug; existing Cnn references are case families, not new task IDs |
| ucId, familyId | `UC-01`, and matching C01–C22; ID prefix must match both |
| datasetId, datasetVersion, caseDigest | Stable corpus identity, immutable version and SHA-256 of canonical public case data; content changes create a new dataset version, never silently relabel a case |
| categories | Nonempty subset of functional, error, edge, safety, integration, model-quality |
| levels, gate | Explicit nonempty supported levels; hard or scored grading gate, with scored permitted only for model-quality samples. Contract/behavior/integration/safety invariants are hard. A level-specific variant has its own caseId if input/oracle changes |
| input | Exactly one product Invocation plus references to admitted public evidence, repository snapshot and catalog fixture; reuse product schema without a competing IssueTicket schema |
| source | Public/synthetic/reporter fixture origin, authorization/licensing reference when applicable, safe source reference and digest; no fabricated repository provenance |
| prerequisites | Required capability/version/profile references, configuration/catalog/policy identities, canonical `catalogDigest` for the complete trusted catalog contents, model requirement, finite bounds, shared owner gates and expected provenance per level |
| gradingRuleId, gradingRuleVersion | Stable rule identity/version; rule implementation belongs to the trusted grader, never model instructions |
| requirements, taskIds | FR/SC references and existing T001–T016 mappings for traceability, not completion state |

`GradingCase` is a separate grader-only record: caseId, datasetVersion, publicCaseDigest, expectedOutcome constraints, expected labels/allowed values, prohibited effects, gradingRuleId/version, oracleDigest and private evidence references. A rule must define exact enum equality/membership, required question/materiality assertions, evidence-support checks and zero-effect assertions as applicable. Semantic-quality rubrics and any human adjudication procedure are approved and versioned before a scored run; no post-hoc label changes to improve a score.

### Proposed canonical digest profile

`uc01-evaluation-sha256-v1` is a DRAFT consumer convention pending Tai/Thai confirmation at X-EVAL-AGREEMENT; it does not select or implement a shared hashing utility. Before T004 freezes data, T002 must validate these exact projections and byte rules:

- `caseDigest` hashes the object `{digestProfile: "uc01-evaluation-sha256-v1", kind: "PublicCase", record: P}`. P contains exactly contractVersion, caseId, ucId, familyId, datasetId, datasetVersion, categories, levels, gate, input, source, prerequisites, gradingRuleId, gradingRuleVersion, requirements and taskIds from PublicCase, including their complete validated nested content. Exclude caseDigest itself, all oracle fields and all execution/result fields.
- `oracleDigest` hashes the object `{digestProfile: "uc01-evaluation-sha256-v1", kind: "GradingCase", record: G}`. G contains exactly caseId, datasetVersion, publicCaseDigest, expectedOutcome, expectedLabels, allowedValues, prohibitedEffects, gradingRuleId, gradingRuleVersion and privateEvidenceRefs. These names make the GradingCase prose fields above explicit; required non-applicable constraints use empty objects/arrays as agreed by the versioned grading schema. Exclude oracleDigest itself and run results. publicCaseDigest must equal the corresponding caseDigest, binding the private oracle to the frozen public case. Only the trusted grader computes/validates G.
- Accept JSON data only: plain objects, arrays, strings with no unpaired surrogates, finite numbers, booleans and null; reject duplicate object keys at parsing, unsupported values and unknown record fields before hashing. Recursively sort object keys by ECMAScript default string sort (UTF-16 code-unit order); preserve array order. Serialize keys and primitive values with ECMAScript JSON.stringify, emitting compact objects/arrays without whitespace; numbers follow that serialization, including negative zero as 0. Preserve string contents without Unicode normalization. Omitted optional nested keys stay omitted; null and absence remain distinct. Equivalent producers must use the same frozen array order; this profile does not silently reorder sets or normalize input text.
- Hash the resulting serialization as UTF-8 bytes without BOM or trailing newline using SHA-256; encode the digest as 64 lowercase hexadecimal characters. Serialization follows the existing UC-03 canonical JSON convention for valid JSON, but this proposal neither imports UC-03 ownership nor authorizes editing its code. A changed projection/encoding requires a new digest-profile/contract version and explicit comparison/migration agreement.

T002 specifies vectors proving reordered object keys hash identically, nested input/oracle changes alter the appropriate digest, null differs from omission, and self-digest/run metadata does not enter either projection. T004 checks independent producers against the same vectors before freezing corpus digests; T015 verifies the real shared adapter preserves this profile or an explicitly approved versioned conversion. These are future acceptance checks, not executed hash tests in this planning revision. Private oracle payloads and low-entropy label digests remain trusted-side metadata and are never exposed to the model or public evidence.

Grade classification, severity, provenance, clarification, destination and safety criteria separately before deriving the case verdict. T002/T004 must include opposite vectors: a valid output with correct classification but semantically wrong severity records correct classification plus a failed severity/case criterion; wrong classification with correct severity records incorrect classification plus the independent severity result. Malformed/unvalidated classification, missing result, evaluator error and not-run have no accepted observed class and contribute zero correct classifications.

Public inputs, goldens and rules for every C01–C22 family are designed in T002–T004, before feature implementation. T002 defines contract/grader positive and negative vectors; T003 defines mock scripts, counters and safe evidence capture; T004 freezes versioned cases, expected outcomes and the held-out selection/grading plan. T015 runs and compares quality evaluations using this prepared design; it does not start dataset design. Held-out labels are frozen before scored runs and kept apart from development/tuning cases; any later expansion is explicitly versioned.

## Grader isolation

Only PublicCase input and permitted evidence enter model context or model-accessible repository tools. GradingCase, expected labels, hidden tests, grader configuration and outputs remain on the trusted harness side, outside the target repository/container and all model read/search mounts. A public case may name an opaque grading rule; it must not contain an expected answer or a resolvable private-label path. Test support builders may hold expected values on the trusted test side, but they must never expose those values to the SUT's ports, prompts, traces or workspace. Check this separation before each run and exercise label-access denial in the security variants. Source/evidence is admitted and bounded before use; fixtures never authorize secret access.

## Machine-readable result proposal

One `CaseResult` per selected case and requested level, including not-run cases:

| Field | Meaning / validation |
|---|---|
| contractVersion, datasetId/version, caseId, caseDigest, oracleDigest | Match the frozen manifest/grader record; oracleDigest is metadata only, not the label payload |
| runId, attemptId, ucId, level, provenance | Unique immutable run/attempt identities; level enum above; provenance mock or real, consistent with the capabilities actually used |
| status | Exactly pass, fail, error or not-run; never coerce absence into pass |
| reasonCode, safeSummary | Stable reason and bounded explanation, mandatory for fail/error/not-run; optional for pass |
| codeRevision, subjectSnapshotDigest, configDigest, catalogId/version, policyId/version | Exact SUT/source/workspace and trusted configuration identities; distinguish slop-loop revision from target-repository state |
| adapterVersions, graderVersion, gradingRuleId/version, capabilityRefs | Actual deliveries and grader used; no invented shared version or mock-to-real promotion |
| startedAt?, durationMs? | Actual execution timestamp and elapsed milliseconds; omitted with reason when not executed |
| metrics | For each classification-scored case record classification correctness as correct, incorrect or not-observed, independently from overall case status, with safe observed-value/private-oracle references. Non-classification cases mark it not-applicable. Aggregate counts/accuracy use this component; latency, input/output tokens and cost carry currency/pricing identity for real calls; metrics tagged observed, unknown or not-applicable with reason |
| traceRefs, evidenceRefs, failureAnalysisRef? | Safe references/digests to isolated artifacts; fail/error requires bounded analysis of mismatch/cause, affected decision, limitation and next verification step |

`pass` means the actual observed SUT behavior satisfies the case's versioned rule at that level. Expected invalid-input/denied product outcomes may therefore be evaluation passes; a product outcome named error is not automatically an evaluation infrastructure error. A malformed model answer in a normal assessment case is an evaluation fail. `fail` is an observed criterion violation; `error` is an evaluator/setup/execution failure preventing valid grading; `not-run` means no execution, with unmet prerequisite, owner/blocker and condition for retry. Unknown usage after a real provider timeout stays unknown/charged under shared accounting, never zero cost. Mock usage is explicitly simulated or not-applicable, never actual provider measurements. Missing required real-run metrics make acceptance incomplete.

Execution-only identity/timing fields may be absent on error/not-run when their prerequisites cannot be resolved; record each missing field and reason explicitly. Never mint a subject snapshot, adapter version or oracle digest for an unexecuted/unavailable component. Selection identity (caseId, dataset version, run/attempt, UC and requested level) remains mandatory.

Results and evidence use immutable `(runId, ucId, caseId, level, attemptId)` namespaces with collision refusal and isolated workspace/config per UC. Never overwrite another UC/run or silently replace a failed attempt with a passing retry. Retain attempt history, reservation/settlement references and the retry policy; select comparable attempts by a predeclared rule. Safe artifacts contain redacted bounded diagnostics and metadata; no raw prompts, protected source, secret labels or credentials in public traces. Storage mechanism, retention and shared result serialization are Tai/owner agreement items, not new UC-01 infrastructure.

## Aggregation, coursework floor and regression comparison

- Proposed manifest fixes the selected case IDs/levels, required subset, dataset/oracle digests, grading rules, target catalog/config and approved thresholds before dispatch. A required-case omission/duplicate is a manifest error, not a smaller successful run.
- Report pass/fail/error/not-run counts, executed coverage and prerequisite reasons separately per UC and level. Every hard-gate case must pass; any required error/not-run prevents acceptance. Incorrect scored model-quality samples remain visible as fail and zero correct answers, but may coexist with aggregate quality acceptance at the approved 80% floor. Report hard-gate verdict, quality score/verdict and execution completeness separately. Never pool mock and real results or average security violations away.
- For model quality, the user-provided SE373 minimum is at least five held-out classification examples covering clear defect, feature request, ambiguous request, irrelevant content and malicious instructions. Proposed anchors: `UC-01:C01:clear-defect`, `UC-01:C07:feature-request`, `UC-01:C06:ambiguous`, `UC-01:C08:irrelevant`, `UC-01:C15:malicious`. These are design identifiers, not files or executed fixtures. Ambiguous/irrelevant cases may have gold undetermined; malicious content is never authority. The approved oracle decides the expected label, safe outcome and rubric before evaluation.
- Classification accuracy is exact correct classification components divided by the frozen required classification-case count, with a minimum acceptance floor of **80%** from the user's supplied requirements. An accepted observed classification matching its gold label counts correct even when severity, provenance, questions, routing or another criterion causes the case to fail. Wrong/missing/invalid classification components and evaluator-error/not-run attempts contribute zero and remain in the denominator. A malformed response with no validated classification is not an accepted observed class. Report the confusion matrix, component correctness and overall case outcomes separately. Independent hard/quality gates still retain their failures; full required execution and safety must pass, so 80% cannot excuse an unrun case, bad severity gate or unsafe action. Other quality/latency thresholds and exact corpus composition still require approval.
- T015 compares at least two actual real-provider runs before/after an identified improvement using the same frozen held-out cases/oracles/rules, catalog and model/provider/config/pricing identities, unless a named treatment variable is intentionally changed. Record the changed code/config variable and every other identity; unrelated drift yields non-comparable, not an improvement claim. Dataset changes require an explicitly shared comparison subset and separate scores. Report accuracy deltas, failure analysis, per-case and aggregate latency, tokens/cost and incomplete accounting. Never tune on hidden labels during a run.

## Standalone execution and shared registration

Thai's future local contract/behavior tests use the existing Node test mechanism with injected ports and consume the versioned case/rule/result design. This is ordinary UC-01 test coverage, not a second evaluation runner. No new command name, package script, executable dataset or shared-runner path is selected by this document.

Proposed registration descriptor: ucId, supportedContractVersions, datasetId/version/digest, publicCaseManifestRef, privateOracleManifestRef (grader-only), supportedLevels, capabilityRequirements, callable consumer-adapter reference, grader-rule references and result contract version. Tai approves the descriptor, registration API, isolation and adapter signatures at X-EVAL-AGREEMENT; X-EVAL-RUNNER proves a real delivery/version. Thai owns UC-01 cases and adapter compatibility tests; Tai owns discovery, orchestration, shared grading infrastructure and one-command project entry point. No platform source edits are part of this revision.

Shared acceptance must prove:

1. Duplicate case IDs within a selected dataset/manifest, conflicting identities/digests at the same version, or a UC-prefix mismatch reject registration before any case runs; different UCs retain distinct namespaces. Versions of the same logical case retain stable IDs in separate `(datasetId, datasetVersion, caseId)` registrations; a run selects exactly one version per case, not an ambiguous unversioned alias.
2. A scoped UC-01 invocation selects exactly UC-01 manifest cases at the requested level, never runs another UC, and records selected-but-unavailable cases as not-run.
3. A project invocation validates an owner-approved required-UC manifest and its required case/attack counts before execution. Unknown/missing required UCs or unavailable registrations produce explicit error/not-run and a non-passing overall result; no UC-01-only fallback may claim project success. Course-wide counts beyond the supplied minimum remain pending original-source confirmation.
4. A failing UC hard-gate/quality verdict or required error/not-run prevents project success without contaminating another UC's artifacts/results. Individual scored failures remain visible under the approved quality threshold rule above. Per-UC results remain inspectable even if the coordinator stops early; later selected cases not executed receive not-run reasons.
5. Register the same versioned UC-01 case definitions/oracles used locally without redesigning the dataset. Adapter/transport conversion is permitted only if case identity, input/oracle/rule digests and status semantics remain intact, with conformance evidence. Real registration unavailable means not-run, not presumed compatibility.

T002–T004 validate the proposed metadata and mock selection/isolation/aggregation obligations locally where possible; they do not implement project discovery. T015 proves actual registration, scoped and project selection, isolation, failure propagation and shared output compatibility when Tai's runner and required deliveries exist. Missing runner/agreement blocks those T015 obligations while earlier authorized local slices may continue. T016 reports UC-01 acceptance separately from whole-project acceptance; global success requires the real shared project run, approved UC manifest and full evidence.
