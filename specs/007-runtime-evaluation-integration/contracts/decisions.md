**Schema-version disposition, 2026-11-11 (planning review P1).** The paragraph above and the approved migration policy in `specs/001-verified-code-repair/contracts/atomic-admission-amendment.md:186` ("UC-03 canonical admission/task-state schema: 0.2.0, replacing 0.1.0 only at the explicit canonical cutover") state different rules for the same schema, and the contradiction was left unrecorded. So §8 changed the v0.1 record in place, which is what the "no bump" sentence describes. The cutover clause is not contradicted in practice — it governs when a 0.2.0 **task-state** schema is introduced and that has not happened — but it was never written to authorize an in-place v0.1 change, and the in-place change is not owner-signed. **Decision: no version bump, and the migration policy is not amended.** A bump now would fork `TaskState` for one optional field with no owner to sign the new schema, and would break every existing v0.1 reader for a change that is already additive-and-fail-closed for mixed readers. The cost is accepted and stated: an unamended reader meeting a clarification state refuses it with `UNKNOWN_PROPERTY` (its allowed-keys list has no `clarification`), not `SCHEMA_VERSION_MISMATCH` — the version still reads `0.1.0`, so the refusal does not identify version drift — and no task may claim otherwise. If a pinned cross-owner v0.1 reader must ever read these states, this decision expires and the §8 successor contract becomes mandatory. This remains a **single-attestation** decision, like the T020–T034 release it sits inside, and G-OWNERS stays unmet.
