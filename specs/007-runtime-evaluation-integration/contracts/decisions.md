## Amendment formalization — 2026-11-07 (later, same day)

On 2026-11-07 (Asia/Saigon), immediately after the agreement above, the user directed that the agreed work be prepared and implemented from the recorded handoff. **Canonical `TaskState` ownership.** §8 adds one optional field and two guarded transitions to canonical `0.1.0`, and the agreeing surface is exactly the seven files it needs: `v01/types.ts` (the field), `v01/clarification-types.ts` (the `ClarificationRecord` shape and `CLARIFICATION_ROUND_CAP`), `v01/validation/state/task.ts` (the `rejectUnknownKeys` allowance and round-trip echo), `v01/validation/state/clarification.ts` (`validateClarification`, which re-derives all three digests), `v01/validation/transition.ts` (the two guarded successors and the `NeedsInfo → Validate` refusal), `v01/admission-context.ts` (six admission-context interfaces split out of `types.ts` by the same change, with no behaviour change), and `identity.ts` (the three constructors those validators call: `computeClarificationQuestionId`, plus the `computeClarificationQuestionDigest` and `computeClarificationAnswerDigest` digests). All seven shipped in commit `58a5a65e` and none is covered by another owner entry. Because every validator calls `rejectUnknownKeys`, a state carrying `clarification` is unreadable by an unamended reader: the change is additive within this release and **not** forward-compatible with a mixed-version reader, and no schema-version bump is intended. It is released at **source/controlled tier only**, and a mixed-version reader refusing such a state is the designed outcome, not a defect. No owner of the canonical v0.1 `TaskState` beyond the one recorded attestation has accepted this specific interface change: the T020–T034 release and this formalization rest on that single user-reported agreement, and no separate canonical-schema owner signature exists. If a pinned cross-owner reader is later required to read these states, this entry does not cover it and a versioned successor contract is needed instead.

**Schema-version disposition, 2026-11-11 (planning review P1).** The paragraph above and the approved migration policy in `specs/001-verified-code-repair/contracts/atomic-admission-amendment.md:186` ("UC-03 canonical admission/task-state schema: 0.2.0, replacing 0.1.0 only at the explicit canonical cutover") state different rules for the same schema, and the contradiction was left unrecorded. What is true in the tree: `TaskState` is defined **only** in `v01/types.ts`, the v0.2 layer defines no `TaskState` successor (`v02/ports.ts:223,280` carry `schemaVersion: '0.2.0'` on the *admission* records, not on task state), and `v01/types.ts:3` still reads `CONTRACT_VERSION = '0.1.0'` with exact equality enforced at `validation/state/task.ts:70-76`. So §8 changed the v0.1 record in place, which is what the "no bump" sentence describes. The cutover clause is not contradicted in practice — it governs when a 0.2.0 **task-state** schema is introduced and that has not happened — but it was never written to authorize an in-place v0.1 change, and the in-place change is not owner-signed. **Decision: no version bump, and the migration policy is not amended.** A bump now would fork `TaskState` for one optional field with no owner to sign the new schema, and would break every existing v0.1 reader for a change that is already additive-and-fail-closed for mixed readers. The cost is accepted and stated: an unamended reader meeting a clarification state refuses it with `UNKNOWN_PROPERTY` (its allowed-keys list has no `clarification`), not `SCHEMA_VERSION_MISMATCH` — the version still reads `0.1.0`, so the refusal does not identify version drift — and no task may claim otherwise. If a pinned cross-owner v0.1 reader must ever read these states, this decision expires and the §8 successor contract becomes mandatory. This remains a **single-attestation** decision, like the T020–T034 release it sits inside, and G-OWNERS stays unmet.

The formalized amendments are [host contract](host-composition.md) §8 (bound clarification: additive `TaskState.clarification`, guarded `Investigate → NeedsInfo → Investigate`, answer-bound continuation input) and §9 (owner-measured isolation: the published v0.1 `CommandView` stays unchanged, and the builder issues a host-owned measured-isolation record that `admissionCommandView` accepts instead of a caller reference).
