## Contract finding: use the existing plan reference as current authority

The smaller alternative is defensible for the local mock route:

- src/approvals/policy-v02.ts validates an approved binding by requiring its decisionId to equal the existing planDecisionRef, then derives the plan digest from that binding. tests/runtime/support/uc03/memory-state.ts makes the same current-state comparison: plan.decisionRef, activeDecisionId, planDecisionRef, and the computed plan digest must agree.
- plan.decisionRef can therefore remain the latest current approval reference. After patch settlement, an owner-only v0.2 operation can set both plan.decisionRef and activeDecisionId to a fresh D1 for the current repository revision. Current check and reviewer admissions then continue to use the existing planDecisionRef and planBindingDigest fields, with D1 in both.
- The accepted plan material remains unchanged: planVersion, strategy, baselineRef, evidenceRefs, criteria, check set, budgets, revision, replan count, and repair accounting are not rewritten. The current planBindingDigest is calculated for D1; the D0 digest in the settled patch admission and receipt remains byte-for-byte historical.
- This avoids currentPlanApprovalRef and any change to PolicyFacts, shared policy facts validation, v0.2 claim/receipt/outcome/reconciliation wire records, or v0.1 ports. Existing v0.2 D0 records remain valid as historical records. They cannot authorize current actions after the owner rebind because current task version, repository revision, plan reference, active decision, digest, and authority generation are checked by existing admissions and claims.
- It is not a graph-only fix. src/uc03/graph-validation.ts and src/uc03/graph-completion.ts currently compare historical patch D0 directly to the mutable current plan reference/digest. Both must instead validate D0 against owner-retained original patch state and issuer evidence, then validate current D1 separately.
- A digest reconstructed from current plan material is only a consistency check. It is not proof that D0 was issued or approved.

## Identity and approval rules

D0 is the decision that approved the original plan before the patch. D1 is a new, distinct decision for that same plan material at the settled current revision and current policy. D1 must be a new unique ID and differ from D0 and every previously issued decision ID. Never mutate D0 or reuse it for a changed repository revision. Pending-to-approved resolution may retain the same D1 only while its immutable binding is unchanged; a rejected D1 is terminal.

The host requests D1 through the existing ApprovalPort and passes only its decision ID to the owner operation. The state owner independently resolves and validates that ID through its configured ContextualApprovalVerifierV02.resolvePlanDecisionInContext using an owner-derived context, as specified below. The request carries no caller-supplied approval object, approved boolean, or issuer assertion. Source code must not invoke fixture-private context setters. If the configured issuer cannot independently resolve and validate D0 under its original revision-bound context, historical ancestry fails closed.

Define requestIdentity as computeCanonicalSha256 of { purpose: post-patch-verification-approval, taskId, runId, originalDecisionId: D0, expectedPlanMaterialDigest, settledRepositoryRevisionDigest, policyIdentity: { policyId, policyVersion, configId, configVersion, issuerKeyRef } }. Derive D1 deterministically as dec-verify- plus the requestIdentity hex digest. Exclude stateVersion, controlVersion, epoch, and decisionAuthorityGeneration from the stable identity; pass them as separate CAS/status fences so pending-to-approved retains the same D1. Repeating the exact request uses the same D1 and one issuer request. Reusing D1 with different material is a conflict.

## Explicit optional contextual issuer contract

The four v0.1 ApprovalPort methods and their signatures remain unchanged. Add a separate optional v0.2 `ContextualApprovalVerifierV02` interface, composed with the owner-configured ApprovalPort and used by the graph through the same trusted composition. Its single public method is `resolvePlanDecisionInContext(decisionId: string, context: VerificationApprovalContextV02): Promise<VerificationApprovalResolutionV02>`. No caller-supplied binding or approved boolean is accepted. Missing capability returns unavailable and zero dispatch; neither a fixture-specific validateBinding overload nor a mutable defaultContext is a fallback.

`VerificationApprovalContextV02` is a closed record containing `purpose` (`historical-patch` or `current-verification`), `expectedIssuerKeyRef`, `expectedDecisionAuthorityGeneration`, and `approvalContext`. All twelve ApprovalBindingContext fields are REQUIRED and non-undefined in approvalContext: currentTaskId, currentWorkspaceId, currentRepositoryRevisionDigest, currentPolicyId, currentPolicyVersion, currentNormalizedActionDigest, currentPlanVersion, currentStrategyDigest, currentBaselineRef, currentEvidenceRefs, currentCriteriaDigest and currentCheckSetDigest. Reject missing/unknown context fields, invalid safe identities/digests, unsafe versions or contradictory evidence. The owner derives these fields from its own original journal snapshot for D0 or its current task/control/policy snapshot for D1. Context supplied by a model, serialized continuation or graph-only copied TaskState is not authoritative.

`VerificationApprovalResolutionV02` is the closed union `{ outcome: 'resolved', decisionId, binding, issuerKeyRef, decisionAuthorityGeneration, contextDigest }` or `{ outcome: 'unavailable' | 'denied' | 'stale', reasonCode }`. contextDigest is the canonical digest of the full requested context. A resolved result means issuer-owned record identity and contextual validation succeeded; it does not mean the status is approved. The binding retains its actual pending/approved/rejected status. The owner and graph require approved before dispatch, and handle pending/rejected using the state-machine table below. Validate returned fields against the request, configured issuer and authoritative snapshot; a structurally matching result from a substituted issuer is insufficient.

The verifier resolves its own issuer records by decisionId, validates ownership/immutable request identity, then applies the existing pure approval-binding validator to the explicit expected context. Pure validation or a caller-recomputed digest alone cannot produce a resolved issuer result. For historical-patch, it loads the immutable approval as issued at the D0 patch's captured authority generation and original revision; a later revocation is not retroactive approval or erasure of that observed effect. If that historical issuer artifact is unavailable, deny ancestry. For current-verification, it resolves the current status at the independently published expected generation and current policy/revision. A status/generation change during lookup returns stale; the state owner also rechecks its control/generation CAS afterward. This is a local mock issuer contract, not real signing/durability evidence.

The graph uses this PUBLIC contextual method for both D0 ancestry and D1 current checks/completion, rather than invoking a ScriptedApprovalPort-only overload. The mock issuer may use its own internal record store to implement the method; runtime source never accesses that store or its private context setters. Add same-issuer D0/D1 success, wrong/substituted issuer/context/generation, missing-capability and pending/rejected regressions through the public interface.

Keep these types in `src/contracts/foundation/uc03/v02/verification-authority.ts` (new) if needed to stay under the source-size limit. Export them through the existing `ports-v02.ts`/`uc03.ts` public facades. Assign `tests/runtime/support/uc03/scripted-approval.ts`, `provider-mocks.test.ts`, `uc03-port-conformance.test.ts`, owner/graph composition and new focused authority tests to implement/forward this exact capability. Existing wire records and the four v0.1 method signatures are untouched.

## Optional v0.2 owner contract

Add only optional fail-closed capabilities to StatePortV02. Missing snapshot, approval-recording, trusted-verifier, or ancestry-loader capability returns incomplete before approval or execution. Keep v0.1 ports unchanged and do not expose generic allowSameNode.

The owner read snapshot has this exact content: taskId, runId, stateVersion, repositoryRevisionDigest, controlVersion, epoch, current decisionAuthorityGeneration, current policyIdentity { policyId, policyVersion, configId, configVersion, issuerKeyRef }, control mode, hold reference, and active claim ID. It is read-only.

Define expectedPlanMaterialDigest as the canonical digest of taskId and every FixPlan material field (planVersion, diagnosis, suspectedCauseLocations, evidenceRefs, strategy, scopedChanges, checkSetDigest, baselineRef, and strategyDigest) plus criteriaDigest. Exclude only decisionRef; this digest therefore proves same material, not issuer approval. The recordVerificationApproval request has this exact content: taskId, runId, workspaceId, repositoryId, D0, D1, expectedStateVersion, expectedRepositoryRevisionDigest, expectedPlanVersion, expectedPlanMaterialDigest, expectedControlVersion, expectedEpoch, expectedDecisionAuthorityGeneration, expected policyIdentity { policyId, policyVersion, configId, configVersion, issuerKeyRef }, and deterministic requestIdentity. Recompute the identity and all material digests from authoritative task state. Treat D1 as a lookup key only. Resolve and validate it under the owner-configured issuer, then re-read state and control and compare every expected version before committing. ApprovalPort.requestDecision uses D1 as an idempotency key: identical concurrent requests return the same issuer record and create one durable request; the same D1 with a different binding conflicts.

The exact result fields are:

    pending = { outcome: "pending", requestIdentity, decisionId, state, controlVersion, epoch, decisionAuthorityGeneration }
    rejected = { outcome: "rejected", requestIdentity, decisionId, state, controlVersion, epoch, decisionAuthorityGeneration }
    approved = { outcome: "approved", requestIdentity, decisionId, state, controlVersion, epoch, decisionAuthorityGeneration }
    conflict | stale | blocked | unavailable = { outcome, requestIdentity, reasonCode }

For the first three outcomes, state is the owner-loaded authoritative TaskState. The approved result contains the committed D1 state; pending and rejected return the unchanged Verify TaskState. Error outcomes carry no authority-bearing state; callers reload.

The result is a closed union:

| Result | Owner effect |
|---|---|
| pending | Return authoritative current state and D1. No task-state, control-version, epoch, budget, or repository change. Graph returns pending and performs zero checks or reviewer calls. The issuer retains this single pending D1 for resume. |
| rejected | Return authoritative current state and D1. Preserve plan.decisionRef at D0 and leave activeDecisionId absent. Enter the existing rejected task-control hold once: controlVersion +1, epoch unchanged, task stateVersion unchanged, no ledger change. Replaying the same rejection is idempotent. No later call auto-resumes it. |
| approved | After issuer lookup says approved and exact current binding validation succeeds, atomically set plan.decisionRef and activeDecisionId to D1, append D1 once to approvalDecisionRefs, and increment task stateVersion and controlVersion exactly once each. Epoch and all other TaskState fields stay unchanged. A successful replay returns the same state without further increments. |
| conflict, stale, blocked, or unavailable | Return a reason code and no authority. The operation makes no task, control, epoch, budget, or repository change. Caller reloads authoritative state; it never falls back to D0 or a caller-created transition. |

Before any issuer request, require Verify state, the expected task/run/workspace/repository and revision, unchanged plan material, runnable control mode, no hold, and no open claim. Recheck all fields under the owner lock after issuer resolution. Same-request callers coalesce; a CAS loser returns the already-committed identical result if the same request won, otherwise conflict. A pending or approved issuer request is never sufficient by itself to dispatch.

A UC-05 pending-to-approved, rejection, or revocation status publication advances the existing decisionAuthorityGeneration exactly once and publishes it through the existing owner authority-control path before the next action. Each publication increments controlVersion once and leaves epoch unchanged. recordVerificationApproval compares the current published generation and its own transition increments above; it does not silently change the generation. If publication races with the operation, the CAS refuses. If revocation races after D1 activation, existing claim/beginAttempt generation checks reject stale admissions; graph code also re-resolves and validates D1 before each current check/reviewer admission. Missing or unpublishable status generation fails closed. This is mock contract behavior only, not a claim that real owner adapters implement it.

The owner also exposes one read-only readSettledPatchAncestry lookup keyed by taskId, runId, and resulting revision. It returns the actual settled Patch admission context, owner-created trusted admission context, nested claim/attempt/outcome/settlement receipt, and original TaskState snapshot from the owner journal. It returns no execution capability. Require exactly one matching settled Patch ancestry for this scoped route; missing, duplicate, unreconciled, or mismatched journal records fail closed. Never accept graph-supplied receipt history as a substitute.

For TaskState-only resume, the graph must restore the actual baseline record as well. Add an optional loadBaselineEvidence lookup to the existing baseline evidence owner, keyed by task/workspace/repository/evidence ID. Validate its returned content against the current task, original revision, baseline reference, criteria, and check set. If graph state already contains the baseline during the same invocation, still validate the owner-retained patch ancestry. Missing baseline or patch evidence during resume returns incomplete before approval/check dispatch; do not fabricate checkpoint history.

For D1, current actions use the existing planDecisionRef=D1 and planBindingDigest=D1. Resolve and validate the current issuer record against the current revision and policy before each command/reviewer admission and again in completion. For D0, resolve its immutable original issuer record and validate it against the original patch TaskState snapshot and original revision-bound context. Verify that the patch receipt still binds the original D0 state, actual owner claim/attempt/outcome/settlement, original repository revision, exact changed paths, and resulting current revision. Separately prove current D1 is approved for the unchanged material and current revision. Deliver clears activeDecisionId in the existing Review-to-Deliver transition; plan.decisionRef stays D1 as the latest current approval reference.
