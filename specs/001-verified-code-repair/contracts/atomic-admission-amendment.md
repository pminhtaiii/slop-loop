# Proposal: Atomic Admission and Durable Effect Attempts for UC-03 / UC-04 / UC-05

## Status and scope

- **Status**: `DRAFT - NOT APPROVED / NOT IMPLEMENTED`.
- **Purpose**: Prepare a focused cross-use-case contract amendment for owner and user review.
- **Ownership**: UC-03/shared foundation proposal. UC-04 and UC-05 owner acceptance is pending.
- **Authorization boundary**: This document does not change an accepted contract, implement T022, update `tasks.md`, or authorize successor work. T022 remains unchecked. Approval of this proposal would still need to be followed by its implementation and acceptance evidence before T022 can be marked complete.
- **Scope**: One UC-04-owned durable admission/control journal; UC-05 remains the policy and human-decision authority; UC-03/shared foundation remains the trusted workspace and effect executor. No second persistence engine and no distributed rollback claim.

This proposal does not supersede [UC-03 contract v0.1](interfaces.md), [UC-05 companion contract `uc05-approval/0.1-draft`](../../../specs/023-uc05-human-approval/contracts/interfaces.md), or [ADR-0007](../../../docs/adr/0007-uc04-task-pause-and-recovery-foundation.md) until the required owners and user explicitly accept a versioned amendment.

## 1. Evidence and current boundaries

The design below is based on these repository facts:

- [UC-03 shared interfaces](interfaces.md) and `src/contracts/foundation/uc03.ts` define contract `0.1.0`. `StatePort` exposes task load/CAS, reservations, settlement, checkpoint and `reconcileUncertain`; it has no serialized effect-attempt operation. `ExecutionGuard.validateAndExecute(action, state)` has no admission context in its current signature.
- [T022](../tasks.md) is unchecked. `src/foundation/execution-guard.ts` is the T021 neutral no-dispatch skeleton; it currently returns denial without calling state, approval, or repository ports.
- `RepositoryPort.applyPatch`, `runCommand`, and `runTests` currently receive no bound admission context. `runTests(check)` is called directly by both baseline investigation in `src/uc03/investigation.ts` and verification in `src/uc03/verification.ts`.
- The current UC-05 `DispatchClaim` in `src/contracts/approvals/contracts.ts` binds claim/action/task IDs, control version/epoch, repository digest, policy identity, decision refs, reservation refs and a lifecycle phase. It does not bind a canonical action payload digest, the separate plan binding, a command-view identity, a task-state version, or a consumed attempt identity.
- `createApprovalContinuation` in `src/approvals/recovery.ts` validates a mock-backed claim receipt and returns a claim ID. It does not execute an effect or grant a generic executor capability. UC-05 T014-T015 evidence is mock-only; T016-T022, real adapters, durability and restart remain gated in its [decision record](../../../specs/023-uc05-human-approval/contracts/decisions.md).
- The current UC-05 companion contract records user-relayed three-owner agreement on `claimDispatch` and says a claim committed first is in flight. This proposal changes that rule because claim creation alone does not prove that the trusted executor consumed the attempt.
- [ADR-0007](../../../docs/adr/0007-uc04-task-pause-and-recovery-foundation.md) requires a paused task to admit no new agent work, allows an already-started bounded call to finish, and forbids blind replay when an effect is uncertain.

These facts establish the gap and implementation boundary. They do not establish real persistence, an executor, a workspace lock, policy-publication serialization, or owner agreement to the proposed protocol.

## 2. Authority and accounting

| Owner | Retained authority in this proposal |
|---|---|
| **UC-04** | The single durable task/control journal, current task state, claim lifecycle, cumulative budget ledgers, outcome journal and recovery decisions. Any atomic transaction described below is one UC-04-owned transaction. The proposal adds no UC-03 or UC-05 store.
| **UC-05** | Action classification, policy evaluation, approval binding and immutable human decision validity. UC-04 stores and compares UC-05 authority references; it does not reimplement policy evaluation.
| **UC-03 / shared foundation** | Trusted action normalization and digest calculation, repository/workspace lock enforcement, immutable command-view construction, and the only route to an effect adapter.

Resource accounting follows the existing owners:

- A repair patch requests one task-scoped `repair` allowance as an actual resource. UC-04 reserves it once with the claim/attempt record; the repair consumer must not reserve it again.
- Repository commands and tests reserve only the actual configured execution resources represented by UC-04 ledgers. They do not incur provider tokens or cost.
- Coder and reviewer model calls keep the existing `ProviderRequest` protocol in `src/foundation/model.ts`: stable request identity, finite token/cost ceilings, one UC-04 reservation before provider transport, observed-usage settlement and retained uncertainty. For an admitted provider call, UC-04 records that existing pre-network reservation with the task claim in one idempotent admission transaction; the claim references the exact `providerRequestId` and reservation receipt but adds no second token/cost reservation. An exact duplicate request reuses that claim/reservation; a fresh request loses before allocating a second reservation while another task claim is open. No provider call routes through `RepositoryPort`, and provider limits do not change.

## 3. Proposed admission record and freshness

The admission request has an explicit subject branch; it never coerces a provider request into a repository action:

- **Pre-plan diagnostic repository action**: only while task state is `Investigate`, UC-05 may classify a bounded `runTests` action for the task's reproduction and required checks, or a controlled test-only patch that adds a regression test allowed by the accepted test policy. Bind task criteria/check-set digests, exact test path/check ID, repository/view revision and action digest. No `planBindingDigest` or `planDecisionRef` is required because no plan exists; no plan approval is inferred. A test-only patch cannot edit production paths or write through a command. Once a test is added, its new revision/check-set digest becomes the bound input for later test runs. Other commands and production patches require a plan-bound authorization.
- **Approved-plan repository action**: repair patches, plan-derived code changes and post-patch verification require the current `planBindingDigest` and `planDecisionRef`, in addition to their own action-policy decision.
- **Provider request**: UC-05 evaluates a proposed distinct `ProviderRequest` subject and issues a `ProviderAdmissionReceipt` bound to stable request ID, coder/reviewer role, exact request-content digest, provider/policy/config identity and current decision-authority generation. This branch does not use `NormalizedAction` or a repository `ActionDecisionReceipt`. Plan applicability is explicit: a pre-plan diagnostic request is limited to `Investigate` and binds task criteria plus the allowed diagnostic purpose; a request made for approved-plan work also binds the current `planBindingDigest` and `planDecisionRef`. Provider policy is required in both cases. UC-05 must explicitly accept this discriminated provider branch and both roles in the new companion contract; it is not an exception synthesized by UC-03.

For repository-action branches, UC-05 evaluates the exact current context and issues a proposed immutable `PolicyEvaluationReceipt`; when human approval is required, it also issues a distinct immutable `ActionDecisionReceipt`. For the provider branch it issues the `ProviderAdmissionReceipt` above. These are proposed contract records, not current API behavior. UC-05 retains the immutable receipts in its existing authority store and authenticates them to its issuer key/reference. UC-04 verifies issuer integrity, exact branch/digest binding and active refs/generations, but does not interpret the policy result. The trusted host prepares the claim request. The final UC-04 transaction must bind and compare all applicable fields below before authorizing an attempt:

- Separate `taskStateSchemaVersion` / `expectedTaskStateVersion` and `controlSchemaVersion` / `expectedControlVersion` / `expectedEpoch`. These are independent version domains and must never be conflated.
- Task, run, workspace and repository identities; current runnable node/mode; current canonical repository revision; and the complete trusted execution-profile/configuration identity.
- The current UC-04 policy/config authority reference, matching the exact UC-05 `policyId`, `policyVersion`, `configId` and `configVersion` used for classification, plus the issuer-key reference used to authenticate the receipt.
- For repository actions, a UC-05 `PolicyEvaluationReceipt` ref/digest bound to the exact action digest, trusted freshness-context digest, policy/config refs, decision-authority generation and result (`ALLOWED`, `APPROVAL_REQUIRED` or `FORBIDDEN`). UC-04 verifies issuer authenticity, branch/digest binding and active refs/generation; UC-05 alone interprets the result. `FORBIDDEN` never admits. `APPROVAL_REQUIRED` also requires an authenticated `ActionDecisionReceipt` bound to this action and evaluation, with a matching active decision-authority generation. For provider requests, the distinct `ProviderAdmissionReceipt` binds its exact request digest and role. UC-05 publishes policy/config/key changes and approval revocations through the UC-04 authority journal; UC-04 compares opaque refs/generations and does not evaluate policy or approval validity.
- The canonical `actionDigest`, recomputed from the exact normalized action and payload bytes at the trusted boundary.
- On an approved-plan repository-action branch, a distinct `planBindingDigest` and `planDecisionRef`, binding plan version, strategy digest, baseline/evidence refs, criteria digest and check-set digest. They are absent on the pre-plan diagnostic repository-action branch. Provider requests follow their explicit plan-applicability rule above: pre-plan diagnostics bind criteria/purpose, and plan-scoped requests bind the approved plan. Action approval refs remain separate; plan approval cannot stand in for an action decision.
- For commands and tests, the exact `CommandView` ID/digest, canonical revision, admitted file digests, exclusions-policy version, scratch identity, read-only mount fact and isolation-profile reference. For a controlled patch, the exact base revision, patch digest and target paths.
- All applicable finite bounds and their trusted profile/config references. A command requires every configured time, output, CPU, memory, process-count and isolation bound. A patch requires its path/breadth and payload bounds. Provider token/cost bounds apply only to the existing provider protocol. No default fills an absent or unlimited bound.
- The exact UC-04 reservation refs required for this operation, including the repair slot when applicable. For provider calls, include the exact request-level reservation receipt. No reservation ref may be inferred from a client-supplied ID.

The repository-policy freshness digest covers task/run identity and state version, exact action and (when applicable) plan bindings, canonical repository revision and command-view/scratch facts where applicable, plus active policy/config refs and decision-authority generation. The provider-receipt digest covers request identity/content, role, plan applicability and applicable plan binding, provider limits/config and active decision authority. The final admission digest additionally binds control version/epoch, complete execution profile and finite limits, reservation refs, and trusted executor/fencing identity.

The plan and action digests are not interchangeable. The `PolicyEvaluationReceipt`, plan decision, action decision and provider admission receipt are distinct records. The executor receives the exact trusted payload, recomputes its digest, and rejects any mismatch before dispatch. The claim stores safe identities and digests, not raw patch bodies, provider content, command output, or protected payloads.

Outcome and reconciliation records retain the same discriminators and plan applicability as the admitted subject. `subjectKind` is `repository-action` or `provider-request`; `planApplicability` is `pre-plan-diagnostic` or `approved-plan` and must equal the value on the claim and the branch-specific UC-05 admission receipt. The variants are:

| Subject and plan applicability | Required branch identity | Fields that must be absent |
|---|---|---|
| Repository action, `pre-plan-diagnostic` | Exact normalized `actionDigest`, `PolicyEvaluationReceipt` reference/digest, any required `ActionDecisionReceipt` reference/digest, diagnostic purpose and criteria/check-set binding | `planBindingDigest`, `planDecisionRef`, provider request/admission fields |
| Repository action, `approved-plan` | Exact normalized `actionDigest`, `PolicyEvaluationReceipt` reference/digest, any required `ActionDecisionReceipt` reference/digest, `planBindingDigest`, and `planDecisionRef` | Provider request/admission fields |
| Provider request, `pre-plan-diagnostic` | Exact `providerRequestId`, request-content digest, `role` (`coder` or `reviewer`), provider-admission receipt reference/digest, provider/config/pricing identities, and the exact request reservation and applicable token/cost/reviewer-iteration budget refs; task criteria and diagnostic purpose | Repository `actionDigest` and action-decision fields; `planBindingDigest` and `planDecisionRef` |
| Provider request, `approved-plan` | The same provider request, role, admission and budget identity, plus the exact `planBindingDigest` and `planDecisionRef` | Repository `actionDigest` and action-decision fields |

The outcome and reconciliation schemas are tagged unions over these variants, not one record with a shared required action-and-plan pair. The exact `actionDigest` is required for every repository-action outcome; provider outcomes instead require their exact request ID/content digest, role, admission ref and budget refs. An absent field on a pre-plan branch is not filled from another receipt, and a provider receipt never supplies repository-action authority (or vice versa). Validators reject missing branch fields, plan fields on a pre-plan record, fields from the other subject branch, or any discriminator mismatch with the claim/admission record. They do not infer a digest or authority from `admissionDigest` alone.

For provider variants, `requestContentDigest` is recomputed from the immutable `ProviderRequest` envelope (task/run, role, purpose, provider/model/config/pricing identities, context digest and finite ceilings). Mutable dispatch state and observed usage are excluded; exact reservation/budget refs are separately bound. This digest definition applies to both outcome and reconciliation records.

The protocol records version progression rather than comparing a later row to an unchanged pre-claim version. Let `S0`/`C0`/`E0` be the task-state version, control version and control epoch used for admission. Claim commit requires that exact snapshot, leaves task state at `S0`, and advances control version to `C1`; the claim receipt records both snapshots. A successful `beginAttempt` must see task state `S0`, the claim's `C1`, the same epoch and active authority refs; it advances control to `C2` and, for a repair patch, persists `Repair -> Patch` and advances task state to `S1`. For command, test and provider work with no task-node change, task state remains `S0`. The attempt receipt records `S0/S1` and `C1/C2` separately. A later state transition is conditional on the attempt's recorded post-begin task version. Outcome/recovery transactions read the current control version and preserve any newer pause/hold; they never overwrite it with `C2`. An unrelated task-state mutation conflicts. UC-04's serial journal identifies allowed control events since `C2`; an unrecognized control mutation leaves the claim open for reconciliation.

Any absent, malformed, foreign, stale, inconsistent or legacy admission context denies before effect. Optional context parameters and implicit legacy dispatch paths are removed at the proposed execution boundary.

## 4. Serialized protocol

### 4.1 Required participants and lock order

The protocol has one UC-04 durable journal and one host-side workspace gate. It does not pretend the repository, database and external effect participate in one distributed transaction.

| Order | Gate | Required behavior |
|---|---|---|
| 1 | **Workspace gate** | Acquire a read lease for an immutable command view, or an exclusive writer lease for a controlled patch. Every trusted writer and view builder must participate. The lease binds the canonical revision and remains held through final admission and effect handoff. A command/test holds it until the executor has opened the immutable view; a patch holds its exclusive lease through the resulting revision and UC-04 outcome transaction. Its fencing generation is checked by the executor before launch. It has no time-based takeover; loss requires fencing the old actor before another holder proceeds. If the workspace cannot provide this guarantee, deny.
| 2 | **UC-04 durable authority/task journal** | One durable journal stores the active policy/config and decision-authority generations/refs, task mode/epoch, independent task-state version, open claims and operation-specific budget rows. It orders claim creation, `beginAttempt`, pause/rejection/direction/recovery, authority publication, reservation and outcome transactions.

UC-05 first stages immutable policy/config or decision artifacts. It then publishes only their active refs/generation with a UC-04 journal transaction. `beginAttempt` reads the same refs/generations and commits against the task claim in that journal. The journal's transaction order decides the race: publication first makes the old receipt stale; `beginAttempt` first admits one attempt under its captured refs. A policy/config change or approval revocation that bypasses this publication operation is not dispatchable. Pause and `beginAttempt` likewise serialize through the task-control row. No UC-04 database transaction or database row lock is held across the external effect; the workspace writer lease remains held through patch invocation and the outcome transaction.

Acquire the workspace gate before invoking a UC-04 transaction, and release it only at the specified handoff/settlement point. UC-04 transactions do not acquire a workspace lock. Policy publication does not acquire a workspace lock. An adapter that cannot follow this order fails closed.

The workspace gate must not rely on an expired lease to make an old executor harmless. The trusted host must reject a stale generation at the executor boundary and confirm the prior actor/process tree cannot launch before releasing or transferring a writer lease. If it cannot, the claim remains open and the task remains blocked.

### 4.2 Admission steps

1. **Prepare without effects.** Validate the action, applicable plan context, current UC-05 classification, workspace mapping, view/patch facts and the complete finite profile. These checks are preliminary and do not grant authority.
2. **Create or recover one claim.** With the workspace gate held, UC-04 atomically reloads task, control and active authority refs; requires runnable state, exact expected pre-claim versions, no open claim anywhere on the task, current policy/config and decision-authority refs, current branch-specific receipts and matching repository/view facts; then records one `claimed` record and binds the full applicable resource refs. This commit leaves task-state version unchanged and advances control version once. UC-04 reserves repair/repository-operation resources here. For a provider request, the same transaction creates its one pre-network reservation or attaches that exact request's already-durable reservation; it never adds a second token/cost reservation. No effect is authorized by `claimed`.
3. **Begin and consume one attempt at the executor ingress.** Only the designated effect adapter's trusted admission gate may call `beginAttempt`; callers and serialized claim receipts cannot invoke that operation as bearer authority. Its recipient is a supervisor-authenticated adapter identity, unique process incarnation and fencing generation, bound with the exact action/payload digest. With the workspace gate still held, the gate takes its per-attempt exclusive mailbox lock and asks UC-04 to compare-and-set the claim from `claimed` to `attempting`. UC-04 rechecks the expected task-state/post-claim control versions, epoch, active authority refs, view/revision, payload digest, current task/control holds and reservation refs in one transaction. Pause/rejection/authority publication or a relevant workspace/state change that wins first denies the attempt. The successful transaction advances control version, creates the unique attempt ID and, for repair, commits `Repair -> Patch` and advances task-state version. It durably records the single-use consumption before returning.
4. **Consume at the receiver, then invoke.** The winning executor ingress validates the returned attempt against its authenticated identity, incarnation, fencing generation and recomputed payload digest, then atomically marks that attempt consumed in a process-local one-shot gate while holding the per-attempt lock. UC-04's attempt record is the sole durable consumption record; the local gate is not a store and cannot authorize another attempt. Only the in-flight gate call that won the UC-04 compare-and-set and local one-shot gate may invoke, while still holding the lock. Exact replays return status only; a second delivery to the same incarnation sees the consumed bit or UC-04's already-attempting state and cannot invoke. If the UC-04 commit response is lost or the process restarts before invoke, the adapter does not retry; the attempt stays open for fencing and reconciliation. A restart has a new authenticated incarnation, which UC-04 rejects for that attempt. If any adapter cannot authenticate its incarnation or atomically enforce this receiver-side compare-and-set, it fails closed.
5. **Record and settle the durable outcome.** The executor returns a branch-matched typed outcome receipt to UC-04. The outcome operation records the immutable receipt and its accounting once, then commits the eligible task/revision transition and claim closure when those state preconditions hold. If the effect is observed but that transition conflicts, UC-04 still records the receipt/accounting and leaves the claim `observed-unsettled` for the predecessor-bound recovery in section 6. A repeated record response acknowledges the stored receipt only; it does not imply settlement completed. No retry invokes the effect again.

`beginAttempt` is both the proposed policy/pause ordering point and the sole durable attempt consumption. It is not evidence that the external effect happened. The executor mailbox lock and process-local consumed bit prevent two deliveries of the same successful attempt to the same process incarnation from launching twice; after restart, the new incarnation cannot reuse the consumed UC-04 attempt. A crash after the UC-04 write but before invoke leaves an unresolved attempt that requires fencing and reconciliation; a read/retry never receives another invocation permit. No database transaction or row lock spans the external effect.

### 4.3 Policy and repository races

- UC-05 policy/config artifacts and decisions are immutable and versioned. UC-04 stores active authority refs/generations; UC-05 evaluates the action and publishes authority changes. If publication/revocation commits before `beginAttempt`, the old receipt no longer matches and dispatch is denied. If `beginAttempt` commits first, its one attempt is admitted under the captured refs; later authority changes apply to subsequent attempts and do not rewrite that attempt.
- A user pause or UC-05 hold that commits before `beginAttempt` rejects it with zero dispatch. If `beginAttempt` commits first, the attempt is in flight under ADR-0007 semantics; a later pause preserves the hold and requests cancellation where supported. Cancellation before launch may settle as proven non-dispatch only when the executor confirms it and the old actor is fenced; otherwise the result remains observed or uncertain. It does not promise rollback.
- A command/test view is immutable and bound to the exact current canonical revision through `beginAttempt`; the executor uses that same view. A controlled patch holds the exclusive workspace gate, verifies the exact base revision and applies the same digest-bound patch. A view or revision drift that wins before `beginAttempt` denies with zero dispatch.
- If the host cannot prove that all canonical writers and the executor participate in the workspace gate, it cannot claim freshness through handoff and must deny the operation.

The proposed policy/decision publication and `beginAttempt` order, single-use executor consumption, and claim-first change are departures from the previously agreed UC-05 0.1-draft claim-first interpretation. UC-04, UC-05 and UC-03 owners must explicitly accept these semantics before they are treated as a contract.

## 5. Claim lifecycle, duplicates and recovery

The proposed lifecycle is `claimed -> attempting -> dispatched -> outcome-recorded -> settled`, with `attempting` or `dispatched` able to become `uncertain`, and a recorded observed outcome able to remain `observed-unsettled` while its required task/revision transition is blocked. `attempting` is the durable, single-use executor consumption immediately before the effect adapter; `dispatched` records confirmed launch when available. `claimed` has no attempt ID. If pause or rejection wins before `beginAttempt`, a distinct `ClaimClosureReceipt` closes the claim only after the recipient has been fenced and the journal proves no attempt was committed. This closure releases unconsumed reservations and does not consume a repair attempt. It is not an outcome receipt and does not fabricate an attempt ID. Uncertain physical effects remain `uncertain` until the existing uncertain-predecessor reconciliation proves an accounted effect or non-dispatch. `observed-unsettled` means the effect and immutable receipt are known, but the required state/revision settlement is not complete; it is not reclassified as physical uncertainty or treated as terminal.

- Every `claimed`, `attempting`, `dispatched`, `uncertain` or `observed-unsettled` claim is open and blocks all further task activity across action IDs, run IDs and consumer instances. That includes a new action with a fresh ID.
- An exact retry of the same claim request returns the original stored claim receipt and reservation refs. It creates no new attempt and grants no permission to invoke. Reuse with a different state, policy, plan, action, view, payload digest or reservation request conflicts and denies.
- The claim is task-wide; `claimId`, `actionId`, continuation ID and `attemptId` remain distinct identifiers. Only the executor identity bound at `beginAttempt` can launch.
- There is no automatic claim expiry, lease timeout, budget refund, worker takeover or replay. Recovery may close an attempt only after it has fenced the old actor and its child process/container from any later launch, and then proves non-dispatch or reconciles the effect. If the old actor cannot be fenced or a physical outcome cannot be established, retain the claim, reservations and task hold as uncertain. If the effect was observed but workflow settlement is blocked, retain the immutable observation/accounting, open claim and task hold as `observed-unsettled` until the recorded receipt can be safely settled.
- Adapter-level deduplication may be used only when that adapter's behavior is explicitly supported and evidenced. This proposal promises at most one authorized executor attempt; it does not claim universal exactly-once effects.

The recommended pause rule is explicit: `claimed` alone is not in flight. Pause-before-`beginAttempt` prevents the launch and requires a fenced `ClaimClosureReceipt`; `beginAttempt`-before-pause commits one logical in-flight attempt, which may then be cancelled or completed but is never automatically replayed. The owners must confirm that the serialized executor ingress and durable one-use consumption are enforceable by every adapter.

## 6. Outcome receipt and atomic settlement

Every attempted effect returns a validated, safe `AttemptOutcomeReceipt` tagged union: `RepositoryActionOutcomeReceipt` or `ProviderRequestOutcomeReceipt`, each further discriminated by the `planApplicability` variants in section 3. Both carry receipt ID/digest, claim/attempt IDs, the exact admission digest, pre-claim/post-claim/post-attempt task-state and control versions/epoch, policy/config and decision-authority refs/generations, the typed outcome (`observed`, `proven-not-dispatched`, or `uncertain`), a safe result/effect reference, the applicable observed usage or exact reservation refs, and the proposed next-state/revision/evidence effects. A repository patch receipt includes its exact observed result revision digest. The repository variant always carries the exact `actionDigest`; plan fields occur only on its approved-plan variant. The provider variant carries the exact `providerRequestId`, request-content digest, role, provider-admission reference and request budget refs; it does not carry a repository action digest. Plan fields occur on either provider variant only when that same provider admission was plan-scoped. Neither branch fabricates fields to satisfy the other branch's schema. Raw output and protected content are excluded.

`AttemptReconciliationReceipt` is also a tagged union over the same four subject/plan variants, further discriminated by `reconciliationKind` (`uncertain-attempt` or `observed-unsettled`). Its subject/plan discriminators and branch identity must match its predecessor exactly. Provider variants use the immutable request-content digest defined in section 3; mutable dispatch state and observed usage are excluded, while exact reservation/budget refs remain separately bound.

- **Uncertain-attempt reconciliation** is accepted only for the exact current `uncertain` outcome receipt ID/digest, claim and attempt. It carries a new reconciliation ID/digest, safe evidence refs/digests and one final disposition: `observed-and-accounted` with actual effect/usage evidence, or `proven-not-dispatched` with adapter evidence plus proof that the old process/tree is fenced and cannot launch. It cannot replace the immutable uncertain receipt with a conflicting outcome receipt.
- **Observed-outcome reconciliation** is the proposed UC-04 `reconcileObservedOutcome` operation and is accepted only for the exact durably recorded `observed-unsettled` receipt ID/digest, claim and attempt. It carries a new reconciliation ID/digest, the same branch-specific action or provider identity, safe evidence refs/digests, and the caller's expected current task-state/control versions and epoch. It does not carry a replacement effect outcome or rewrite the observed receipt. The receipt already records the known physical effect; this operation resolves only its blocked state/revision settlement.

The repository/provider operation happens outside the UC-04 transaction; no database lock or transaction is held across the effect, while the patch's exclusive workspace writer lease remains held through patch invocation and outcome recording. The protocol does not claim a cross-system atomic effect.

UC-04 `recordOutcome` performs one idempotent transaction over its journal, state, budget and claim records. It validates the exact open claim, attempt, receipt branch/digest, attempt versions and task identity; appends the immutable outcome and safe journal reference; and accounts for the effect exactly once against the exact reservation refs. Observed provider usage is settled against the recorded pricing identity even if the response is invalid. An uncertain outcome retains its full unresolved reservation. A proven non-dispatch may release only provider/execution resources that evidence proves were unused and only after the old actor is fenced; it never refunds a repair allowance consumed by `beginAttempt`. A repair allowance consumed by `beginAttempt` is not charged again by outcome recording. A repository-only action creates no provider token/cost charge. Any hold or control update after `beginAttempt` is preserved by reading and advancing the current journal version, never by writing stale `C2`.

If the required task-state/revision/evidence transition is consistent, the same transaction writes the resulting repository revision and eligible task transition, invalidates stale command views, baselines, approvals, verification and review evidence, preserves the current pause/rejection/ended/recovery hold, and closes the claim. If an effect is observed but that transition conflicts, the transaction still commits the immutable outcome receipt and its one accounting decision, marks the claim `observed-unsettled`, leaves task state/revision unchanged, and preserves the task hold. It does not treat a failed state CAS as non-dispatch or lose the receipt. An outcome result of `settled` means the state/revision/evidence transition and claim closure committed. `recorded-unsettled` means the receipt/accounting are durable but that transition is pending. A duplicate `recordOutcome` response is status-only (`already-recorded`); it never implies settlement completion. A conflicting receipt is rejected without another accounting or state write.

The caller recovers an `observed-unsettled` claim from the recorded receipt through `reconcileObservedOutcome`; it never invokes the effect again. UC-04 reloads the exact predecessor receipt, claim, current task/control records and repository evidence. For a patch, the current repository revision must match the receipt's observed result revision. The current task row must either remain the exact post-`beginAttempt` state for that attempt, or differ only by a journaled version/checkpoint advance while every semantic task, run, workspace, plan, action and repository binding remains identical. An already committed successor is recognized only from the same stored reconciliation result. Any other task/repository mismatch remains blocked and leaves the observation, accounting, current versions, hold and open claim intact. The operation applies only the successor and evidence invalidations already authorized by the stored attempt; it does not accept caller-supplied replacement state or new policy/approval authority.

When the predecessor is eligible, `reconcileObservedOutcome` appends a separate immutable settlement/reconciliation receipt, applies the transition at the reloaded task-state version, advances the current UC-04 control version without restoring an old epoch/mode, writes the exact observed repository revision and invalidates the recorded stale evidence once, then closes the claim. The task/control versions in the settlement receipt show the actual current-to-next progression. The current pause/rejection/ended/recovery hold remains in force, so claim closure never implies new work is runnable. Replaying the same reconciliation ID/digest after restart or a lost response returns the same settlement result without a second accounting event or state transition. A different recovery ID/digest after closure, a stale predecessor, or a conflicting receipt returns conflict and cannot reopen the claim.

This distinction is explicit in the result sketch:

| Operation/result | Meaning |
|---|---|
| `recordOutcome` → `settled` | The immutable receipt, one accounting decision, eligible state/revision/evidence transition and claim closure committed. |
| `recordOutcome` → `recorded-unsettled` / exact replay → `already-recorded` | The receipt and accounting are durable; task settlement is not asserted. Reload/recover from the same receipt. |
| `recordOutcome` → `uncertain` | Physical outcome is not established; retain the unresolved reservation and open claim for uncertain-predecessor reconciliation. |
| `reconcileObservedOutcome` → `settled` | The exact recorded observed predecessor was settled once; exact-key replay returns the same settlement result. |
| `reconcileObservedOutcome` → `blocked` / `conflict` | No state overwrite or reexecution; retain the recorded observation, accounting, open claim and current holds. |
| `reconcileUncertain` → final or still uncertain | Only an exact uncertain predecessor may be reconciled; unknown physical effects remain charged and blocked. |

The existing `reconcileUncertain` journal path validates that its predecessor is still the current uncertain receipt, then atomically appends its branch-matched final reconciliation, settles or releases only the applicable reservation under the evidence, advances revision/task state if justified, invalidates stale evidence, preserves concurrent holds and closes the claim. A proven non-dispatch may release a provider/execution reservation only when evidence proves that resource was not used; it never refunds a repair attempt once `beginAttempt` consumed it. Repeating the same reconciliation ID/digest after a lost response returns the original final receipt without a second settlement. A stale uncertain receipt, a different final receipt, or a second reconciliation after closure conflicts and cannot reopen the claim or invoke the effect again. A failed execution or failed checkpoint alone never proves non-dispatch and never refunds a consumed repair attempt. Uncertain physical effect cannot be finalized through `reconcileObservedOutcome`, and an observed-unsettled receipt cannot be submitted to `reconcileUncertain`.

For a claim closed before any attempt, the host submits a `ClaimClosureReceipt` to the proposed UC-04 `closeUnattemptedClaim` operation in the same journal. The receipt binds claim ID/digest, acquisition versions, current pause/denial event, executor fencing identity/generation, evidence that no `beginAttempt` committed and disposition of each reservation. UC-04 accepts it only while the claim is still `claimed`, proves no attempt exists, verifies the recipient cannot later launch, releases only unconsumed reservations, and closes the claim atomically. It carries no attempt ID. This closure adds no separate recovery store.

For a repair patch, `beginAttempt` persists `Repair -> Patch` before the patch call and consumes the repair allowance once. A successful outcome settlement persists the new repository revision, `Patch -> Verify`, evidence invalidation and claim closure. If an observed patch cannot commit that transition because of a compatible state-version conflict, keep its receipt and accounting and settle from that exact receipt after reloading; never apply the patch again. If the effect result itself is lost or uncertain, use the uncertain-predecessor path and inspect/reconcile the repository; never invent an observed receipt. A failed or partially applied patch attempt consumes its repair attempt. Only a proven no-invocation result before `attempting` can release an unconsumed claim reservation, after the old actor is fenced. Failure alone is not a repair refund.

A command/test nonzero exit is an observed effect outcome, not a verified non-dispatch. It is settled against the exact applicable resources. A provider response or timeout continues through the existing provider usage/reconciliation protocol; its outcome carries provider-specific request/budget identity, and repository-only work records no provider token or cost.

## 7. Consumer and seam alignment

The amendment requires all effectful paths to use the same mandatory admission context and executor:

- `ExecutionGuard` accepts a required trusted context and produces a typed claim/attempt/outcome receipt. A real executor cannot start without the complete context. Each adapter's trusted admission gate authenticates its unique process incarnation and fencing generation, serializes deliveries per attempt, atomically consumes a process-local one-shot bit backed by UC-04's durable attempt record, and invokes only from the winning gate call. UC-04 remains the only durable admission/accounting store.
- `RepositoryPort.applyPatch` receives the exact base revision and required admission context. `runCommand` receives the exact immutable `CommandView`, isolation profile and finite limits. `runTests(check)` is lowered by trusted code to a canonical `run_command` action bound to the exact check ID, structured executable/argv, purpose, view and limits; the wrapper sends it through the same guard and cannot launch directly.
- Baseline reproduction in `src/uc03/investigation.ts` and verification in `src/uc03/verification.ts` must use the guarded `runTests` path. The pre-plan diagnostic variant permits the required baseline and controlled test-only regression-test patch during `Investigate` without a fabricated plan decision; a production patch remains denied until its plan binding and required approval exist. Missing context or any applicable bound denies before process creation.
- `src/uc03/repair.ts` remains responsible for validating repair evidence, current approved plan and the proposed patch. It supplies the repair allowance request to the guard. The guard/UC-04 transaction owns the single reservation, `Patch` persistence, attempt claim, effect receipt settlement, revision update and `Verify` transition; repair does not reserve or CAS those same effect transitions a second time.
- Read/list/search remain behind the current trusted read capability and must check current task-control admission. An open effect claim or pause/approval hold blocks subsequent task activity.
- `src/foundation/model.ts` continues to use the current provider request protocol and reservation identity. Coder and reviewer requests each require their own provider-branch `ProviderAdmissionReceipt`; plan fields apply only to plan-scoped provider work, while the explicit pre-plan diagnostic variant binds task criteria/purpose. Before provider transport, the authenticated provider adapter obtains the same task-wide claim/`beginAttempt` admission using the exact `ProviderRequest`; UC-04 creates or attaches its single pre-network reservation in the claim transaction. The branch-matched outcome records that exact request, role and budget identity and settles observed usage once; it closes the claim only when eligible state/revision settlement commits, otherwise an observed-unsettled claim remains open for its receipt-bound recovery. It does not reserve again or use `RepositoryPort`.

All real callers and port wrappers must be updated together. There is no optional context overload, automatic legacy fallback, or production mock path. Explicit mock fixtures may exercise the new validators and races, but mock passes do not satisfy real-conformance, adapter, isolation, durability or restart acceptance.

## 8. Proposed schema versions and migration

This is a breaking contract change. If approved, the proposed versions are:

- UC-03 canonical contract and task-state schema: `0.2.0`, replacing `0.1.0` for guarded execution.
- UC-05 companion claim/control records: `uc05-approval/0.2-draft`, replacing `uc05-approval/0.1-draft` for new claims.

The new records add distinct task-state/control schema and version fields; UC-05 policy-evaluation, action-decision and provider-admission receipts; active policy/config and decision-authority refs/generations; action and plan digests; workspace, repository and command-view refs; complete finite profile refs; exact reservation refs; unique attempt and authenticated executor/process-incarnation/fencing identities; UC-04's durable consumed-attempt state plus the required process-local receiver gate; `ClaimClosureReceipt`; branch-discriminated repository/provider `AttemptOutcomeReceipt` and `AttemptReconciliationReceipt` variants; and the immutable observed-outcome/settlement journal records. Validators reject unknown, missing, malformed, foreign or cross-branch fields. The UC-05 version bump also updates `SafePresentation` and CLI records that share or emit the approval schema; all producers, validators and consumers migrate together to `0.2-draft` unless UC-05 owners explicitly approve separate record versions and compatibility rules.

Migration work must update canonical types, validators, exports, all adapters and forwarding wrappers, mock ports, provider/control composition, and conformance suites in one versioned change. Preserve and adapt the existing `StatePort.reconcileUncertain` path through the UC-04 journal; do not add a parallel recovery store. `src/approvals/control.ts` and `src/approvals/recovery.ts` must preserve their existing approval/continuation meaning while refusing to treat an old claim ID as executor authority. The Phase 6 `createApprovalContinuation` remains admission-only until separately authorized compatibility work adds a validated executor handoff.

An old unresolved claim is not backfilled with invented attempt, view or authority data. UC-04 must reconcile it using its current evidence before enabling the new protocol. Task-state `stateVersion` and UC-05 control `version`/`epoch` stay separate in storage and in every receipt. Old or unknown records that cannot be reconciled remain blocked; they never authorize a new effect.

## 10. Deterministic acceptance matrix

Every listed test is a future acceptance requirement after the owner-approved version exists. Use deterministic barriers at prevalidation, workspace-lock acquisition, authority-ref read/publication, claim commit, `beginAttempt`, receiver-side consume, immediately before low-level invoke, observe, settle, checkpoint and recovery. Assert dispatch count, reservation count and refs, exact digests, each protocol-owned state/control version, task hold, open-claim set and repository revision.

| Case | Required result |
|---|---|
| Policy/config publication wins before `beginAttempt` | Old receipt is stale; zero invocations. Any reservation from the already-created claim remains held until a fenced actor and proven non-dispatch receipt permit its closure.
| `beginAttempt` wins before policy publication or pause | One attempt is admitted under the captured refs; later policy/hold remains active for next work; cancellation is requested where supported and settles only as observed or proven non-dispatch after fencing, otherwise uncertain.
| Pause/rejection wins after claim but before `beginAttempt` | `beginAttempt` denies; a tagged `ClaimClosureReceipt` closes the still-claimed record only after recipient fencing and proof no attempt exists. It carries no attempt ID, releases only unconsumed reservations and consumes no repair attempt.
| Repository writer/view drift wins before `beginAttempt` | Zero invocation. If the command view is already pinned and `beginAttempt` wins, the executor uses those exact bytes; a patch always checks the locked base revision.
| Duplicate successful receipt to the same executor incarnation | Deliver the identical successful `beginAttempt` receipt twice concurrently to one authenticated adapter incarnation. Hold the one delivery that passes the serialized gate at the pre-invoke barrier while the duplicate arrives; only one may reach that barrier. Release it and assert one low-level invocation while the duplicate sees consumed/status only. Restart the process and verify its new incarnation cannot reuse the UC-04-consumed attempt. A lost response never yields a second invocation permit.
| Version progression through acquisition and attempt | Starting from task/control `S0/C0/E0`, claim commit records `S0/C1/E0`; begin commits `S0/S1` and `C1/C2` for a repair patch, or unchanged task state for command/test/provider work. These own increments succeed; an intervening unrelated task-state update or stale control snapshot denies.
| Fresh action/run ID while any claim is open | Deny task-wide; `claimed`, `attempting`, `dispatched`, `uncertain` and `observed-unsettled` all block.
| Stale or duplicate executor actor after reconciliation | Old attempt cannot launch after the owner increments/fences the generation; reconciliation refuses closure if the old actor/process tree may still launch.
| Crash or lost response at every boundary | Re-read UC-04 state. Same outcome receipt is idempotent; unknown invocation remains uncertain and blocked; no blind retry, refund or takeover.
| Settlement/checkpoint failure after patch | A compatible task-state/revision conflict records the immutable observed receipt and one accounting decision as `observed-unsettled`; recovery from that receipt commits the exact `Patch -> Verify` transition and invalidations once, or keeps the claim/hold blocked. No second patch.
| Uncertain and observed-outcome recovery | Uncertain reconciliation accepts only the exact uncertain predecessor; observed recovery accepts only the exact observed-unsettled predecessor. Each has a distinct tagged variant. Lost responses and duplicate recovery are idempotent; conflicting/stale replays cannot rewrite receipts, double-charge, reopen claims or invoke effects. Current task/control versions and holds are preserved.
| Failed/partial repair attempt | Charge the repair attempt if `beginAttempt` occurred; do not refund just because the patch or later verification failed.
| Pre-plan baseline and test-only regression path | During `Investigate`, guarded baseline `runTests` succeeds with no plan decision; an allowed test-only patch may add the regression test under accepted test policy. A production patch with no approved plan binding is denied with zero dispatch.
| Provider request/claim race | Same request ID reuses the one claim and pre-network reservation; a fresh competing request is denied without another reservation or transport; observed usage and uncertain charge retain current semantics.
| Provider branch for coder and reviewer | Positive coder and reviewer requests each carry a valid provider-specific admission receipt; pre-plan diagnostic requests bind task criteria/purpose, plan-scoped requests bind the approved plan. Each launches through the one-use executor with exactly one pre-network reservation and no duplicate reservation.
| Pre-plan outcome and idempotent settlement | A pre-plan baseline test, test-only regression patch, and diagnostic provider request each settle using their own tagged receipt variant with no fabricated plan. Exact receipt replay does not repeat accounting or imply transition completion. Repository variants require `actionDigest`; provider variants require exact request ID/content digest, role, admission receipt and budget refs.
| Cross-branch outcome/reconciliation fields | Missing required branch fields, fabricated pre-plan plan refs, provider fields on repository receipts, repository action/decision fields on provider receipts, mismatched plan applicability, or reconciliation against the wrong predecessor are rejected without filling fields from another record or changing accounting/state.
| Observed patch plus task-state conflict | Record an observed patch and its one charge, inject a compatible task-state version conflict, restart, then reconcile from the exact stored receipt. Assert no patch replay, one settlement/transition, exact result revision, invalidated evidence once, monotone task/control versions and preserved pause/rejection holds. An incompatible state/repository change remains blocked with the receipt and claim retained.
| Provider budget regression | Provider request ID, pre-network reservation, observed usage and uncertain charge remain unchanged; repository actions create no token/cost entries and no repository provider route appears.
| Patch workspace gate lifetime | A competing canonical writer and command-view builder remain blocked during patch invocation and until settlement commits, or until fenced recovery proves the writer actor cannot proceed. No UC-04 database lock/transaction remains open across invoke.
| Uncertain receipt vs final reconciliation | A conflicting outcome receipt cannot replace U. Only `reconcileUncertain` with the exact uncertain predecessor can finalize it; observed-unsettled recovery uses its separate exact predecessor operation. Repeated final reconciliation is idempotent, stale/conflicting records fail, and holds/accounting remain unchanged after replay.
| Version migration and old continuation receipt | Canonical validators/producers, `SafePresentation`, CLI output, plan-context and CLI consumers, mock store/context/fixtures/recovery and wrappers migrate together. Old launch authority rejects, and `claimId` from current mock continuation alone never launches an effect.
