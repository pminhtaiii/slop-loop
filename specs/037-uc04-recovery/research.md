# Research: UC-04 Recovery Foundation

This is a repository-grounded design assessment, not a technology benchmark or approved backend choice. All sources are local authoritative documents; no external technology claim needs online research. Open owner choices remain explicit release dependencies in [decisions](contracts/decisions.md), rather than guessed defaults.

| Topic | Decision / status | Rationale | Alternatives considered |
|---|---|---|---|
| Delivery boundary | Reuse accepted ADR-0007 foundation-first scope | Real storage/restart can be tested with scripted seams before unfinished workflow integration | Waiting for all UCs obscures independent recovery work; claiming integrated delivery from seams overstates evidence |
| Schemas | Reuse canonical 0.1.0 and accepted UC-05 companion records | Shared consumers already validate these identities/transactions | Forking schemas or editing foreign artifacts would create incompatible authorities |
| Deliberate pause | Propose separate durable pause record and joint admission predicate; G-EXTENSION remains open | Approval modes cannot express deliberate pause's bounded in-flight behavior; UC-05 directions cannot silently become UC-04 resume | New approval mode requires a joint migration; one overloaded boolean loses independent holds |
| Durable backend/checkpointer | Defer selection to Thanh Tan at G-STORE; require actual transaction and process-crash conformance | Existing stack explicitly leaves storage open; orchestrator dependency proves no persistence | Embedded SQL, server database and file-backed journal are candidates, with no winner claimed; memory-only cannot prove durability |
| Recovery authority | State/checkpoint plus trusted current repository/outcome evidence | Summaries/traces explain but cannot authorize replay or spend | Conversation-only restoration loses atomic accounting; unconditional replay repeats uncertain effects |
| Budget protocol | Reuse durable multi-reservation, claim, observed settlement and retained uncertainty | Both model roles and task/run scopes share one ledger | Post-call estimates, role-specific fresh balances and automatic reservation expiry violate accepted accounting |
| Feature strategy | Preserve UC-03-only materiality semantics; defer generic feature strategy contract | Persisting three UC-03 replan slots does not assign feature workflow behavior | Copying the UC-03 route or cap onto every feature would decide outside scope |
| Evidence tiers | Separate local mock behavior, real-store process restart and actual integration | Kill/restore can prove foundation storage with controlled external seams; real approval/executor obligations remain | Same-process reconstruction and CLI child loss with parent memory are insufficient durability evidence |
| Retention/control/reconnect | Gate exact surface, deletion policy and retry/backoff | ADR-0007 records desired control/history but leaves mechanics open | Inventing CLI grammar, TTL or provider retry could erase holds or create duplicate billable effects |

The initial source inventory included all documents requested by the user: AGENTS and context index/planning/workflow; project overview, architecture, state, runtime policy, permissions, stack, testing and glossary; delegation, relevant matrix rows, ADR-0004/0006/0007; UC-03 and UC-05 spec/plan/tasks/interfaces/decisions/acceptance/data model. [Decisions](contracts/decisions.md) records base-versus-IDE provenance and the UC-03 authorization conflict. These findings permit conditional design, not implementation readiness.
