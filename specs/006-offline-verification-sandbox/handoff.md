## B. Current architecture and authority boundaries

The developer-only [helper](../../scripts/prepare-verification.ts) selects a trusted workspace, obtains an exact local confirmation and calls [`prepareVerification()`](../../src/sandbox/preparationcoordinator.ts). [`createLocalPreparationConfiguration()`](../../src/sandbox/preparationcomposition.ts) reads private policy/quota evidence and composes concrete adapters. [`PreparationStorage`](../../src/sandbox/preparationstorage.ts) admits a bounded action against a trusted effective Linux whole-builder boundary; an exclusive private action file fences independently composed helper invocations. A missing or unsupported quota mechanism blocks before preparation effects. This production composition currently rejects `process.platform !== "linux"`; Windows Docker Desktop quota admission is **not implemented**.

The [`DockerPreparationRuntime`](../../src/sandbox/preparationruntime.ts) uses a private [`DockerPreparationNetwork`](../../src/sandbox/preparationnetwork.ts) and [`ConnectBroker`](../../src/sandbox/connectbroker.ts) for fixed, restricted fetch. [`runPreparationWorkerPhase()`](../../src/sandbox/preparationworker.ts) runs pinned pnpm 12.5.1 fetch with hooks/scripts disabled and obtains exact artifacts. The trusted coordinator validates the frozen lock graph and SRI of actual tarball bytes ([downloads](../../src/sandbox/downloads.ts), [package content](../../src/sandbox/packagecontent.ts)), then offline-materializes and checks the complete pnpm tree, peer placements, links, bins and generated metadata ([normalization](../../src/sandbox/normalization.ts), [dependency tree](../../src/sandbox/dependencytree.ts)). [`freezeAndSeal()`](../../src/sandbox/frozentransfer.ts) and the [safe importer](../../src/sandbox/safeimport.ts) bind producer identity and transfer content. Approved exact-identity scripts run only in a fresh, offline CAS-free recipient ([offline scripts](../../src/sandbox/offlinescripts.ts)); post-script bytes are checked again. [`PreparedImagePublisher`](../../src/sandbox/preparationpublication.ts) validates frozen content, constructs an application-owned build context, inspects and smoke-checks an immutable image ID, then atomically writes a private READY record after cleanup and accounting can settle. Private ownership journals precede staging/build effects; they are not a complete restart reconciler.

For verification, [`workspaceSnapshotSource()` and `compareWorkspaceCurrent()`](../../src/sandbox/workspacesnapshot.ts) use the Phase 4 [WorkspaceBoundary](../../src/workspace/boundary.ts) and safe held handles to copy eligible bytes, exclude denied content and compare fresh hashes. [`VerificationAttempt`](../../src/sandbox/attempt.ts) retains one sealed snapshot and full-check coverage across calls. [`LocalDockerPort`](../../src/sandbox/localdocker.ts), [`DockerSandboxBackend`](../../src/sandbox/docker.ts) and [`VerificationCoordinator`](../../src/sandbox/verification.ts) execute each approved tests/lint/typecheck/build check in a fresh offline container, with native source rebuilt from the snapshot where required. The [gateway](../../src/sandbox/gateway.ts), [runner](../../src/orchestration/runner.ts) and trusted receipt boundary reject partial, stale, cross-attempt, replayed or boolean-only completion. Final checkout comparison and exact cleanup acknowledgements fence completion and slot release. The model and repository cannot choose the Docker endpoint, flags, mounts, preparation policy or dependency scripts.

## E. M4 — durable cleanup and recovery handoff

M4 owns residual F02/F09 and T162 integration. Persist resource owner, workspace/task/action, generation, engine/container/image/staging identity and cleanup state **before** external effects. On process start, rebuild cleanup holds and preparation reservations before admitting another task/action. Reconcile only positively owned containers, staging, preparation networks, broker resources, build contexts and images against current immutable IDs/labels; never global prune or remove a conflicting/unrelated resource. Exact task/resource/generation acknowledgements alone may settle a hold. Cancellation, timeout, process crash, daemon outage, late result, repeated signal and cleanup failure must remain bounded and fail closed; an ended task never regains execution authority.

M3 lock/journal records provide ownership material but are **not** an M4 restart-recovery implementation. Required source/security tests: process restart reconstructs a hold; wrong/stale/replayed acknowledgements do not release it; daemon disappearance and uncertain process termination retain accounting; repeated signals do not silently end bounded cleanup; unrelated resources survive; only confirmed owned cleanup permits new admission. Follow with real daemon-loss/restart fixtures in M5. Do not mark T162 complete from source tests alone.

Do not pull/build/install automatically to make a fixture pass.

Execute current production code, not parallel fake journeys. Prove: held-handle snapshot capture and exclusion of secret/nested/mounted/hard-linked/alias inputs; content/mode drift and final freshness; four fresh offline writable clones of one snapshot with read-only dependencies; changed TypeScript and `.cc` source changing actual results; same-clone offline native prelude; trusted receipts, canonical result and cancellation fencing; network none for verification and confirmed broker-only fetch with no direct bypass; exact locked actual-byte SRI; real pnpm 12.5.1 multiversion/peer/bin/metadata equivalence; frozen producer/export and safe import; CAS-free exact-identity script execution; sanitized context, immutable image inspection/smoke/atomic record; and no checkout writeback.
