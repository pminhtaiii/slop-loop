# Use disposable offline containers for verification

Status: Implemented and verified in Phase 5 under PR #167 / CI run #54. Q1–Q23 design choices implemented and verified on the native Linux Docker daemon.

The Phase 5 design session on 2026-10-02 keeps the trusted Slop Loop application on the host and uses Docker only for verification. A trusted verification verdict captures one workspace-filtered snapshot; every check in that verdict runs in its own fresh Linux container cloned from that same snapshot. Initial targets are TypeScript repositories, starting with Slop Loop itself and trusted pnpm profiles. PostgreSQL, Redis, and other supporting services are outside MVP scope. Verification containers run offline. Future browser research requires a separately designed capability and does not grant network access to verification.

## Settled decisions (Q1–Q23)

- The MVP targets TypeScript repositories, initially Slop Loop itself, with trusted pnpm verification profiles.
- A verification verdict is bound to one captured current-working-tree snapshot. Capture passes through the trusted workspace boundary and includes approved edits and eligible untracked files while excluding `.git`, denied secrets, nested repositories, host `node_modules`, and stale/generated artifacts.
- Hash the bytes actually copied into the snapshot manifest, with relevant metadata. Rescan eligible checkout content to detect observed capture races. Retry capture a bounded number of times; stop verification if a stable snapshot cannot be obtained.
- Every check in a verdict (tests, lint, typecheck, build, and repository-owned native compilation where required) uses a fresh container clone populated from the same captured snapshot. Rebuild required repository-owned native addons offline from that snapshot inside the check container.
- After the checks, compare the current eligible checkout with the original snapshot manifest. Results remain valid evidence for that snapshot; when the checkout differs, mark the verdict stale for the current checkout and require fresh verification.
- Capture is not an atomic filesystem snapshot and cannot prove that a rapid external change-and-restore race did not occur. File watchers may provide an advisory signal, but never serve as authority. Atomic filesystem snapshots and excluding external writers are deferred.
- There are no supporting services in the MVP. Linux verification applies on Windows and Linux hosts; Windows-specific checks remain for developer/CI workflows.
- Verification has no network access. The developer explicitly triggers preparation. The agent cannot enable network, install dependencies, or rebuild the image.
- **Q20 — Authority boundary:** target-repository files, configuration, and code are untrusted data/code. Only the trusted runtime supplies execution policy and authority.
- Preparation fetches declared and locked dependencies, including required transitives, from approved public registries with restricted network access and installation scripts disabled. Installation/build steps that execute code run offline. Preparation has no developer secrets, sensitive host directories, Docker socket, or writable mount of the real checkout.
- **Q18 — Locked-artifact integrity:** preparation fetches only exact locked artifacts; trusted preparation validates sources, restricts destinations to approved public registries, rejects redirects outside approved destinations, and verifies lockfile integrity hashes. Unsupported sources or integrity failures block preparation. The linked Phase 5 plan selects the mechanism; implementation and adversarial proof remain open.
- **Q21 — Trusted image recipe and dependency scripts:** the preparation recipe is application-owned trusted configuration. A target repository's Dockerfile is never executed and cannot select Docker privileges, mounts, network access, or build instructions. Downloading keeps lifecycle/build scripts disabled; a dependency lifecycle/build script may execute only offline and only when trusted configuration explicitly allowlists that exact locked dependency identity. Unsupported scripts block preparation until the developer updates trusted configuration. Repository-owned native compilation is a separate trusted profile. The linked Phase 5 plan selects exact-identity enforcement; implementation and adversarial proof remain open.
- Initial dependency support is limited to approved public registries and patterns required by this repository. Private registries, Git/SSH dependencies, arbitrary tarball URLs, and other unsupported sources are rejected.
- The preparation fingerprint covers dependency manifests, lockfile, approved package-manager configuration, Node/pnpm versions, Linux architecture, base-image digest, preparation recipe, and dependency lifecycle/build-script allowlist. Source-only edits do not invalidate it; fingerprint drift reports a stale image and blocks verification pending developer preparation.
- **Q22 — Developer-triggered preparation:** Phase 5 includes a minimal preparation helper; the later interactive CLI may expose it. When the runtime detects a stale image, it reports and explains the stale state. It may offer/start preparation only after explicit developer confirmation. The model cannot initiate preparation, supply that confirmation, or enable network access.

- **Q23 — Stale-task lifecycle:** After reporting a stale image, the current task ends in terminal `BLOCKED` without rolling back approved edits. Preparation runs only after explicit developer confirmation through the trusted helper. Once preparation builds a new image, Slop Loop admits a new task, reevaluates the current repository state, captures a fresh snapshot, and verifies it. The blocked task does not resume; task authority is not restored, while session-scoped file grants remain subject to the existing new-task admission contract. In both the immediately valid-image path and the post-preparation new-task path, the image fingerprint must match the dependency data captured for that verification snapshot; a pre-snapshot image check alone is insufficient.
- Dependency-owned native components may be prepared once and bound to the fingerprint. The image supplies compiler/build tools, Python where required by `node-gyp`, matching Node headers, and dependencies. Missing prerequisites block execution.
- Initial per-check resource defaults are 2 CPUs, 4 GiB total memory including tmpfs, swap disabled, 256 PIDs, and 300 seconds wall-clock including native compilation. Each limit is also constrained by the remaining active-task deadline and any stricter trusted profile timeout. There is no automatic resource expansion; only trusted developer configuration may change limits. These are MVP starting values, not benchmark-proven, and must be validated during Phase 5 integration.
- Repository code and dependency installation scripts are treated as malicious. The MVP uses hardened Docker with non-root execution, dropped capabilities, no privilege escalation, default seccomp, and tightly restricted writable paths. Its residual container/kernel escape limits must be explicit. A dedicated disposable VM is deferred for future reconsideration.
- **Q15 — Cleanup failure:** attempt bounded stop/removal retries. If the runtime cannot confirm stop/removal, block further verification and report the container identity and uncertain state. On startup, reconcile only Slop Loop-owned resources. Never fall back to host execution.
- **Q19 — Writable paths:** only the copied snapshot and build artifacts under `/workspace`, plus `/tmp`, are writable. The system directories, toolchain, and root filesystem are read-only. The developer checkout is never mounted writable, and verification output is never copied back automatically.

## Phase 5 planning resolution and proof gates

- The developer-requested [Phase 5 plan](../../specs/006-offline-verification-sandbox/plan.md) and [research](../../specs/006-offline-verification-sandbox/research.md) select initial output/storage/snapshot/download/retry limits and enforcement mechanisms. These are planning defaults, not measured or implemented guarantees.
- Q18 uses a validated frozen artifact graph, fixed trusted no-hook/script fetch, integrity checks and temporary approved-public-destination broker with no direct bypass; required adversarial fixtures must prove enforcement.
- Q21 checks every exact locked occurrence before generating pnpm's name-keyed script permission. Allowlist changes invalidate the fingerprint; scripts remain offline. Version-confusion fixtures are mandatory.
- Immutable image/profile/input identities, bounded tmpfs/staging and private ownership records are specified in the plan/contracts. Linux Engine and Windows Docker Desktop fixture evidence, including preparation storage enforcement, is required before integration readiness.
- The Phase 4 exit gate is complete for available fixtures: PR #164 / CI run #41 verified implementation commit `0b990c03718fa9ae9f1f33de230f9cf53ff38d71` on Windows and Ubuntu. Linux bind-mount containment remains UNVERIFIED / UNAVAILABLE under the accepted, unchecked T088 MVP exception; it is not a PASS and does not independently block Phase 4 completion. Phase 5 implementation may begin, while its own exit gate remains open. Unsupported Phase 5 enforcement or unavailable required Phase 5 fixtures block Phase 5 readiness rather than enabling a fallback.

These choices accept preparation and startup overhead to avoid dependency downloads during agent verification and state contamination between checks. Snapshot and result rules keep a verification verdict tied to the exact bytes copied even when the live checkout changes later. Phase 5 remains planned. Future browser research requires a separate capability policy and does not enable networking in verification containers.
