# Count model turns, tool calls, and internal events separately

Status: accepted design; implementation pending.

Phase 1 currently charges a single `agentSteps` counter for model proposals and several trusted lifecycle events. This makes the amount of reasoning available to a task depend on how many internal events its implementation emits. Before real tools are integrated, an agent step will mean a model turn. Tool invocations will have a separate count, and internal lifecycle events will not spend either count merely because the runner processes them. Trusted admission and policy will set finite limits; the model cannot increase them.

This decision supersedes ADR 0004 only where it says each automatic event consumes an agent step. The existing Phase 1 code retains that behavior until the budget refinement is implemented and verified. `coding-agent-context/context/progress-checker.md` continues to describe implemented reality.

The MVP budget profiles are fixed as follows:

| Profile | Model turns | Tool-call attempts | General retries | Active work time |
| --- | ---: | ---: | ---: | ---: |
| Small | 30 | 60 | 3 | 30 minutes |
| Medium | 60 | 120 | 5 | 30 minutes |
| Large | 120 | 240 | 8 | 30 minutes |

Task admission seals the initial profile, permitted promotion edges, trusted triggers, cumulative-accounting semantics, and Large as the absolute maximum. It also fixes one shared general-retry ceiling from the initial admitted profile. Verification/repair, model recovery, and ordinary policy-denial recovery consume that same counter, with the reason recorded. The active profile may advance only within the sealed schedule through trusted budget policy; promotion raises model-turn and tool-attempt capacity but never replenishes or increases the admission-time retry ceiling. Neither the coding model nor a later file grant can alter the schedule or numeric limits.

These limits are design choices for initial measurement, not claims that a task of a given size needs those amounts. Active work time includes model and verification execution and excludes waits for developer input. Internal lifecycle events consume neither model turns nor tool-call attempts. Each model-submitted tool call consumes one tool-call attempt when individually dispatched to the gateway, including malformed, unknown, and policy-denied calls. Undispatched proposals in the same model response consume no tool attempts. Jev selects the initial size category through the tested three-option `Choice` response; trusted admission maps a valid choice to this fixed table only when the probability of that choice is at least 0.7. A valid choice below 0.7, failed classification, or unusable response selects Medium. The returned probabilities are retained as evidence. The threshold belongs to trusted admission policy; the coding model cannot select a profile or numeric limits. There is no separate wall-clock ceiling in the MVP. Provider token and cost limits remain separate later-phase controls.

Work-capacity limits are model turns and tool-call attempts; when a Small or Medium task reaches one while continuing work, trusted budget policy may promote it once to the next fixed profile. Usage is cumulative; promotion does not reset counters or the 30-minute active-work clock. Recovery limits cover verification/repair retries, model recovery, and denial recovery. An ordinary policy denial consumes a tool attempt, and a model recovery explicitly requested after that denial consumes an applicable recovery retry. Exhausting any recovery limit terminates at the current active profile without promotion, whether denied calls were identical or different; no similarity heuristic is used. Large is the maximum profile. Terminal exhaustion of any finite limit—including Large model/tool capacity, the active-work deadline at any profile, or an applicable recovery limit—produces `BUDGET_EXHAUSTED` and a bounded developer-facing handoff for a later task. The handoff states the exhausted budget, configured limit, and observed usage where applicable, then includes the objective, meaningful completed actions, changed paths, verification state, blockers or unresolved state, exact stop reason, and remaining steps. It is input material for a new task, not a restorable session, capability token, or continuation authority; canonical audit retains bounded metadata rather than raw conversation or repository content. The existing Phase 1 code has no promotion or automatic handoff; the progress checker remains the source of implemented status.
