# Read-only target repository questions through agentic search

On 2026-11-12 (Asia/Saigon), the user confirmed that the initial repository question-answering use case will use the existing controlled repository tools: `searchCode` and `readFile`, with `listDir` supporting navigation. The agent chooses and refines search terms, inspects source, and follows discovered relationships to answer questions about functions, files, cross-file flows, and repository design. The evidence source is the approved target Python repository, separate from the slop-loop implementation and hidden evaluation judging material.

The historical 2026-11-12 approach (superseded for UC-02 below) used bounded agentic exploration without BM25 or semantic indexing. BM25 would add lexical ranking, but its benefit has not been established for this scope; semantic retrieval remains a possible future extension. Repository files are eligible evidence subject to existing workspace and protected-data policy, rather than all being loaded into every prompt.

The agreed tool changes are match locations and match-centered excerpts for `searchCode`, and line-range reads for `readFile`, retaining workspace containment, protected-content filtering, revision checks, and output limits. Answers must cite inspected source locations from the examined revision, distinguish architectural inference from direct observations, and state insufficient or conflicting evidence. The question-answering agent is read-only: it lists, searches, and reads without modifying files or executing target-repository code; source inspection does not establish executed behavior.

The harness will validate that citations identify source locations actually read at the examined revision. This establishes citation provenance; evaluation must separately judge whether those locations support the answer's claims.

Answers must use evidence from a consistent examined repository revision. If the repository changes during investigation, invalidate affected evidence and re-read it before answering; earlier findings cannot be silently combined with a new revision. Follow-up questions are supported within a product session containing multiple tasks. Reuse earlier evidence only after checking its repository revision. Preserve relevant conversation through possible context-window compaction, keeping user statements distinct from repository observations; conversational memory does not establish current source evidence or action authority.

Clarification is an evaluated behavior rather than a prompt-only assurance. The agent must not invent user goals, unsupported premises or author intent. Evaluate both missed and unnecessary clarification, including ambiguous references, missing intent, unsupported premises and requests beyond the read-only scope. Cases must identify when clarification is needed versus when the inspected evidence supports proceeding. A request to modify or execute repository code does not expand this question-answering agent's authority.

Search limits will be configurable. Initial defaults will be selected through experiments across repository sizes and budget levels, measuring answer quality, relevant evidence found, latency, cost, and tool usage. Budget exhaustion must be visible as incomplete investigation rather than treated as evidence that a behavior is absent. Numeric limits and any size-based adjustment policy remain undecided.

Evaluation will cover function explanations, cross-file behavior, architecture questions, and insufficient-evidence cases, including questions without implementation identifiers. Maintain a stable regression set and an exploratory development set that grows from inspected failures, with a separate held-out set to assess generalization. Agents must not access hidden judging material. Retain inspectable run evidence for searches, files and ranges read, tool errors, usage, timing, final answers and citations within existing protected-data and trace rules; this does not authorize unrestricted raw tool-output or prompt logging. Failure analysis should distinguish retrieval failures from misunderstanding evidence already read.

This records the agreed design direction and tool-improvement scope, not an implemented capability, completed feature specification, or release of gated shared-owner work. Precise tool contracts, numeric budgets, evaluation acceptance criteria and compliant trace representation remain to be defined before implementation. Evaluation will exercise a separate target repository and judge answers against evidence; no new evaluation machinery is established by this decision.

## 2026-11-13 — UC-02 retrieval amendment

The initial literal-only retrieval decision above is superseded. The approved Python target, snapshot provenance, tool protections, budgets, active-session follow-ups and judging isolation still govern. UC-02 adds syntax-based source chunks, local embeddings, a persistent vector index, and deterministic fusion of exact definition names and cosine retrieval. Read and validate source through the existing guarded boundary before answering.

Use SQLite with sqlite-vec to keep the manifest, vector metadata and generation publication under one local transaction boundary. Reuse unchanged vectors across process restart and file-level refresh. Windows and CI compatibility and bounded operation are required before accepting that choice. multilingual-e5-small is the first measurement candidate; select a different candidate if Recall@5 falls below 0.8. Keep source-coordinate validation automatic and judge semantic support separately. See [retrieval](../../specs/008-retrieval-augmented-generation/contracts/retrieval.md) and [evaluation](../../specs/008-retrieval-augmented-generation/contracts/evaluation.md).
