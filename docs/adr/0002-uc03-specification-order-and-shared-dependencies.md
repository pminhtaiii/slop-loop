# Specify UC-03 behavior before its shared foundation details

Accepted on 2026-10-15 during the UC-03 design discussion. Draft the UC-03 behavior specification first, using the agreed user outcome and completion criteria to identify its dependencies. Discuss and specify workspace boundaries, execution environment, libraries, and tools in the next session; finalize the UC-03 implementation plan and task ledger after the shared contracts are agreed. Specification order differs from implementation order: real execution depends on integrated foundation components. This decision does not approve feature artifacts or authorize implementation.

Preserve the ownership in the [use-case delegation map](../use-case-delegation.md): Tai owns shared repository tools, controlled execution and isolation, and evaluation infrastructure as foundation work; UC-03 composes them for the bug-fix workflow. UC-04 owns persistence and recovery, and UC-05 owns action classification and the approval gate. UC-03 must not duplicate those implementations. The shared action gate and required isolation must be integrated before real repository changes; deferring that gate until after real execution is not an accepted shortcut.

Mocks may exercise workflow branches against agreed contracts during development. End-to-end UC-03 verification requires real tools operating on a controlled disposable Python/pytest repository with a seeded bug and enforced execution boundaries; mocked command results alone are insufficient. Exact environment and tool designs, library choices, and the remaining specification split are open. A narrow first slice does not waive the fuller UC-03 verification requirements in the [target matrices](../progress-checker-matrices.md).
