# UC-04 begins with a task-scoped pause and recovery foundation

Accepted with the project owner on 2026-10-20 (Asia/Saigon). Build UC-04's durable state, checkpoint, budget, pause, and recovery foundation against controlled seams before integrating the unfinished UC-03 workflow, UC-05 decisions, and shared executor. This is a planning boundary, not authorization to implement or evidence that restart recovery works. UC-04 retains the storage and recovery authority established in the shared contracts; it does not duplicate approval policy or tool execution.

For the MVP, a user-requested pause targets one selected task. Other tasks, including those in other projects, continue. The task presents one `paused` state immediately and admits no new agent work. An already started bounded tool call may finish under its existing limit, including a test suite or a file modification. The harness records the result for the agent to inspect after resume; the pause does not initiate another tool call or promise to undo an in-flight effect. The owner preferred this over adding a user-visible `pausing` state because the extra status would complicate the first control experience without helping the user decide what to do. The harness may track outstanding work internally. A resume request while such work remains outstanding is declined; the user may retry after the result is recorded. This favors a settled recovery point over starting work against an incomplete result.

This user-requested pause is distinct from UC-05 approval and rejection holds. [ADR-0006](0006-uc05-cli-and-human-control.md) still governs those holds, including its rule that background investigation stops while approval is pending or rejected. Neither pause nor resume overrides an approval hold, an uncertain effect, or a spent allowance. If the in-flight result cannot be established, recovery retains uncertainty and forbids blind replay.

After an unplanned runtime process restart, a task that was not deliberately paused may continue automatically only after the harness restores and validates its saved state, repository assumptions, accounting, and unfinished effects. A deliberate pause survives restart and still requires explicit resume. The owner confirmed this distinction on 2026-10-20. Network/provider reconnection is a separate failure mode: bounded backoff was suggested for later design, but a request with an uncertain dispatch or billable outcome cannot be blindly retried. The exact control surface and storage backend remain open.

When recovery finds repository changes not explained by saved tool results, re-inspect the current files and reassess affected assumptions without asking the developer about routine drift. Do not overwrite those changes merely to recreate an old checkpoint. If the task already appears complete, use the owning workflow's verification capability when available and report its actual evidence. This does not bypass UC-05: a changed repository digest makes an existing bound plan approval stale under the agreed current contract, so a fresh decision is required before the affected approved action. The owner confirmed this boundary on 2026-10-20. Controlled UC-04 foundation tests may model the verification and approval ports; real integration remains later work.

The first UC-04 delivery uses a scripted multi-step task and controlled approval/tool seams to exercise durable state, pause, cumulative accounting, process termination, restore, and safe continuation. Actual process restart evidence is required for the foundation's durability claim; an in-process mock is insufficient. The delivery preserves authoritative task state and the compact summary needed for resumed reasoning. Reusable repository knowledge across different tasks belongs to a later UC-04 phase. This staged scope was confirmed by the owner on 2026-10-20 and does not claim the feature workflow or other use cases are integrated.

Successful automatic recovery does not send a separate explanation of restored fields or the next agent action; the owner considered that narration unnecessary. Ordinary task completion reporting still follows the owning workflow. For the local MVP, completed task state and recovery history remain available for developer inspection and explicit deletion. Unresolved approvals, effects, and accounting cannot be deleted merely because the visible task appears complete. Retention format, authorization, and deletion mechanics remain for planning.

If recovery cannot safely continue, notify the developer with a concise reason and the action needed to unblock it. On explicit status inspection, show the task goal, completed steps, current hold or outstanding operation, and next safe action. These exceptional and requested views provide control without narrating every successful restoration. The owner confirmed both presentation rules on 2026-10-20.
