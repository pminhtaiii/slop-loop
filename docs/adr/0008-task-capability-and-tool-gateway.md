# Seal task authority and authorize tool calls through one gateway

Phase 3 seals each task's maximum authority at admission: task and session identity, workspace identity, fixed mode, eligible tools and capability classes, resource limits, and trusted budget promotion schedule. Exact path-operation file permissions live in a separate revocable grant ledger; a later grant can satisfy authority within the ceiling but cannot expand it. This keeps permissions discovered during an Edit task possible without allowing a grant to change the task's mode, tools, workspace, or budgets.

Every model-submitted tool request passes through a mandatory `ToolGateway` before an executor can run. The gateway checks schema validity, the sealed ceiling, current grants, policy, and budget state, and calls the executor only on an explicit `ALLOW`. `PolicyEngine` remains a side-effect-free decision component; missing or invalid authority and policy exceptions deny execution. This establishes an enforceable invocation boundary while preserving the registry's validation and visibility role from ADR 0005.

The closed tool catalog is the single trusted source for a tool's name, input and output schemas, risk/effect metadata, mutation or execution classification, required capability, timeout/runtime limits, and maximum output size before that tool becomes executable. Phase 2's non-executable registry remains intentionally narrower; Phase 3 and later owning phases complete the entries without creating a competing policy tool-name map. Configuration may select or narrow trusted definitions but cannot give the model authority to edit them.

The application exposes only the gateway-facing invocation interface; executor references remain inside the gateway composition. Phase 3 tests use a fake executor to prove that runner calls pass through the gateway and that only allowed calls reach the selected executor. The MVP permits one in-flight tool call per task so budget, permission, stop, and checkout effects have deterministic order. Only a proposal individually dispatched to the gateway counts as a tool attempt. On the first ordinary `DENY` in a model response, the runner discards that response's remaining undispatched proposals and decides whether to spend one shared recovery retry before requesting a fresh model response. For each dispatched call, the gateway assembles a fresh trusted decision context containing the current task state, sealed ceiling, grants, budget, workspace facts, network policy, approved profiles, and executor readiness as relevant; that context is discarded after the call and never reused across calls or sessions. `PolicyEngine` receives this context rather than fetching state itself.

A policy decision distinguishes `ALLOW`, `NEEDS_FILE_PERMISSION`, and `DENY`. Missing exact write permission can produce `NEEDS_FILE_PERMISSION` only after other eligibility checks pass; neither that result nor `DENY` executes anything. After a developer grant, the request receives a fresh full evaluation. An ordinary `DENY` may lead to bounded model recovery, spending a general retry when the runner asks the model to recover. `FAILED / POLICY_FAILURE` terminates when internal authorization fails or required trusted authority state cannot be safely evaluated. `BLOCKED` denotes an external dependency or environment condition while authorization remains healthy.

Audit evidence is a dispatch prerequisite, not an authorization authority. `PolicyEngine` does not read audit contents or availability. The gateway records bounded request identity and a validation or policy decision for every individually dispatched model-submitted call, including unknown and malformed calls, without persisting raw arguments. For eligible calls, canonical request and decision evidence must be successfully appended before invoking any model-visible tool, including read-only tools. An unavailable sink or failed required append yields `BLOCKED / AUDIT_UNAVAILABLE` and zero executor calls. The ordering is request, validation/policy evaluation, durable request/decision evidence, executor invocation, then result evidence. Phase 3 proves this with a fake audit sink, while Phase 12 supplies the real append-only JSONL writer. The gateway never falls back to unaudited execution.

If result-evidence persistence fails after an executor may have produced an effect, the gateway immediately notifies the developer and stops further model-visible dispatch. It makes a small bounded number of synchronous persistence retries through an idempotent audit interface keyed by stable `event_id`; it never replays the executor. The append contract detects whether the event was already committed before retrying, preserving the hash chain without duplicate events. If persistence remains unconfirmed, the task is `BLOCKED / AUDIT_INCOMPLETE` and reports the completed or possibly completed effect. A durable background retry queue is deferred.

Executor output remains untrusted until the gateway validates it against the registered output contract, enforces size bounds, and normalizes, sanitizes, and redacts it. Only the resulting bounded metadata and model-visible result may leave the gateway; raw unbounded output never enters canonical audit. A persistent effect is not undone or disproved by an invalid result, and the gateway must not rerun its executor. It reports the effect status separately from a typed `TOOL_CONTRACT_FAILURE` and stops unsafe continuation pending checkout reconciliation.

Phase 3 consumes trusted canonical repository-relative path facts through a narrow workspace-boundary contract. It does not resolve paths, symlinks, or containment. A validly evaluated forbidden path receives ordinary `DENY`; if required trusted path facts cannot be produced or validated, the task terminates as `FAILED / POLICY_FAILURE` with no execution. Phase 4 owns a separate `WorkspaceBoundary` module that validates the checkout and supplies real path facts before integrated filesystem enforcement is claimed. Phase 3 tests use a fake workspace boundary and first reconcile the Phase 1 runner with ADR 0006's budget accounting and ADR 0007's fixed task mode before connecting it to the gateway.

Each model-submitted tool call consumes one tool attempt when it reaches the gateway, including malformed, unknown, and policy-denied calls; internal lifecycle events do not consume attempts. A denial recovery also consumes a bounded general retry when the runner asks the model to recover. Exhausting denial recovery terminates at the current active profile without promotion; no identical-call or similarity heuristic is used. Stopping a task rejects new calls, signals an in-flight executor to abort, fences late results from further state transitions, and holds the active checkout slot until mutation is impossible and required cleanup completes before `CANCELLED`. Later adapters must honor that contract.

An externally changed target invalidates its existing file permission. Restoring old bytes does not reactivate that grant; a later use requires fresh developer authorization. Git status alone cannot establish that target identity and observed content remained unchanged. The permission ledger advances its observation after the agent's own authorized write, while later write adapters recheck target identity at point of use under ADR 0001.

Read tools require capability and path-policy approval but no per-file developer prompt. A valid exact update/create grant may be reused across Edit tasks and bounded repairs while the same in-memory CLI session remains open, provided the next task's sealed ceiling allows it and fresh repository checks pass. Switching to Ask, `/clear`, or CLI exit revokes grants. Reopening an ended session is deferred from the MVP; the append-only audit stream preserves evidence, not restorable conversation context.
